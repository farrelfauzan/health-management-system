# GitHub Pull Request Skill

## Goal

When asked to create a pull request, analyze the current changes and produce a GitHub-ready PR description.

Do NOT invent changes. Base everything on the git diff, commit history, or files modified.

---

## Workflow

1. Inspect the current branch.
2. Compare it against the target branch (typically `main` or `develop`).
3. Review:
   - changed files
   - commit messages
   - git diff
4. Understand the purpose of the change.
5. Produce a complete PR description.

---

## Output Format

### Title

Use Conventional Commit style whenever possible.

Examples:

- feat: add OAuth login
- fix: prevent duplicate invoice creation
- refactor: simplify cache manager
- docs: update installation guide
- perf: reduce API response latency

---

### Description

```md
## Summary

Briefly describe what this PR does.

## Changes

- Change 1
- Change 2
- Change 3

## Why

Explain the motivation behind these changes.

## Testing

- [ ] Unit tests
- [ ] Integration tests
- [ ] Manual testing

### Tested By

Describe how the feature was verified.

## Screenshots

If UI changes exist, include screenshots.

## Breaking Changes

None

## Checklist

- [x] Code follows project conventions
- [x] Self reviewed
- [x] Tests added or updated
- [x] Documentation updated if needed
```

---

## Guidelines

### Write for reviewers

Assume reviewers know the codebase but not the implementation details.

Prefer:

- what changed
- why
- impact

Avoid explaining every line of code.

---

### Summaries

Good:

> Adds retry logic to API requests to improve resilience during transient failures.

Bad:

> Updated api.ts.

---

### Changes Section

Use concise bullet points.

Example:

- Added JWT refresh support
- Improved error handling
- Refactored authentication middleware
- Added unit tests

---

### Testing

If tests are detected:

List them.

Example:

- npm test
- pnpm test
- pytest
- cargo test

If no tests exist, explicitly state:

> No automated tests were added.

---

### Breaking Changes

Only include if applicable.

Explain migration steps if necessary.

---

### Screenshots

If frontend files changed:

Ask for screenshots if unavailable.

---

### PR Title Rules

Keep titles:

- under 72 characters
- imperative
- concise

Good:

```
feat: support multiple workspace members
```

Bad:

```
This PR introduces a whole bunch of changes to the authentication system
```

---

## What NOT to do

Do not:

- invent features
- exaggerate
- include AI-generated disclaimers
- include "Generated by AI"
- mention ChatGPT
- speculate about intent

---

## Tone

Professional.

Concise.

Reviewer-focused.

Use Markdown compatible with GitHub.
