## D-022: BPJS PCare Protocol Confirmation and Codec (P11-T01 Spike)

- **Status:** Accepted
- **Decision:** Adopt the community-documented PCare REST v3.0 wire protocol as the basis for the Phase 11 adapter, and land it as a pure codec utility in `apps/api/src/common/bpjs-pcare/` (`buildBpjsPcareHeaders`, `decodeBpjsPcareResponse`, typed `BpjsPcareCodecError`) with pinned fixtures. Defer live dev-environment verification until a facility-issued credential set exists.
- **Why:** BPJS publishes no official SDK and the Trust Mark portal is login-gated; the de-facto specification is the community reference implementations. Two independent PHP implementations ([antmey/bridging-bpjs](https://github.com/antmey/bridging-bpjs), [fadlyyy/bpjs-pcare](https://github.com/fadlyyy/bpjs-pcare)) agree exactly on every protocol detail below, and the spike's fixtures were additionally cross-checked against the openssl CLI (HMAC signature and AES layer byte-for-byte).
- **Consequence:** `P11-T02` builds the signature interceptor, config, and resilience layer on this codec unchanged. Because the response AES key is derived from the request timestamp, the adapter must generate the timestamp once per request and keep it until the response is decoded. Protocol facts are pinned in unit fixtures so a BPJS-side change fails loudly in CI, not silently in production.

### Confirmed protocol (PCare REST v3.0)

Request headers, rebuilt per request:

| Header            | Value                                                                                         |
| ----------------- | --------------------------------------------------------------------------------------------- |
| `X-cons-id`       | `consId` as issued                                                                            |
| `X-Timestamp`     | Unix seconds UTC, as a string                                                                 |
| `X-Signature`     | `Base64(HMAC-SHA256("{consId}&{timestamp}", secretKey))` (raw digest, then base64)            |
| `X-Authorization` | `Basic Base64("{pcareUsername}:{pcarePassword}:095")` — `095` is the fixed PCare `kdAplikasi` |
| `user_key`        | `userKey` as issued                                                                           |

Response envelope is `{ metaData: { code, message }, response }`. `metaData.code` arrives inconsistently as string or number — the `P11-T02` adapter normalises it. When `response` is a string it is encrypted; error envelopes carry plain JSON (or nothing) and pass through undecoded. Decode order for encrypted payloads:

1. `keyMaterial = SHA-256("{consId}{secretKey}{timestamp}")` (raw 32 bytes) where `timestamp` is the value sent on the request; IV = first 16 bytes of the same hash.
2. AES-256-CBC-decrypt the base64 payload with that key/IV (PKCS#7 padding).
3. LZ-String `decompressFromEncodedURIComponent` the plaintext (dependency: `lz-string`, the reference JS implementation the PHP ports derive from).
4. `JSON.parse` the result.

Failure taxonomy in the codec: `BPJS_PCARE_RESPONSE_MALFORMED` (body or decoded payload not JSON, envelope missing), `BPJS_PCARE_DECRYPT_FAILED` (padding/key mismatch — typically a timestamp reuse bug), `BPJS_PCARE_DECOMPRESS_FAILED` (decrypt "succeeded" but plaintext is not LZ-String data). Messages never carry credentials, derived keys, or payload content.

Conventions confirmed alongside: dates are `dd-MM-yyyy`; base URL `https://new-api.bpjs-kesehatan.go.id/pcare-rest-v3.0` (production; a separate dev base is issued with credentials); code systems are BPJS-specific (DPHO for medications, BPJS's own ICD-10 list, kd-coded poli/dokter/kesadaran/tindakan).

### Open item: facility credentials

Dev credentials were **not** obtainable in this spike: BPJS issues them per facility through its branch office (kantor cabang) under an active PKS, and HMS cannot register as a vendor ([bpjs-pcare.md](./bpjs-pcare.md) §1). ## D-023: Antrean Online (Mobile JKN) Is Its Own Phase, Not a Phase 11 Task (P11-T08 Evaluation)

- **Status:** Accepted
- **Decision:** Adopt antrean online bridging as a product commitment, but **do not build it in Phase 11**. Land the evaluation as [bpjs-antrean-online.md](./bpjs-antrean-online.md) and schedule the work as Phase 14 (`P14-T01` … `P14-T06`), gated on a pilot clinic that already runs PCare bridging in production, a branch-office request for the **separate Antrean-service credentials**, and a deployment with a public IP that someone is accountable for. The one piece that is buildable today — per-poli queue numbering (`P14-T01`, the `P8-T06` follow-through) — is buildable independently and carries no BPJS dependency.
- **Why:** Antrean online is a second integration wearing the D-022 protocol, not a seventh PCare endpoint. Three properties put it outside Phase 11's shape:
  1. **It is bidirectional.** Everything Phase 11 built is HMS calling BPJS. Here BPJS calls HMS: the facility must host _get token_, _status antrean_, _ambil antrean_, _sisa antrean_, _pasien baru_, and _batal antrean_. `ambil antrean` and `pasien baru` are writes into bookings and patient master data reachable from the public internet — HMS has exactly two public routes today (`auth`, `health`), and neither writes. That is a new security boundary deserving its own review, not a task tacked onto a finished phase.
  2. **It cannot be proven without BPJS.** The PCare adapter was verified end to end against a signature-verifying fetch stub precisely because HMS was always the caller. The inbound contract is the facility's to publish and is confirmed only at BPJS's UAT (_Dokumen UAT Bridging Antrol v2.0 FKTP_, with a signed pakta integritas and a branch-office profile flag before Mobile JKN lists the clinic at all). Fixtures would test our reading of a thin, FKRTL-contaminated spec, not the spec.
  3. **Its prerequisites are outside the codebase.** Separate consId/secretKey/userKey issued for the Antrean service; poli, doctor, shift, and quota published from **HFIS**, which HMS cannot write; a public, always-reachable host. A self-hosted clinic behind NAT cannot run this feature no matter what ships.
- **Consequence:** `P11-T08` closes as an evaluation, and Phase 11 is complete. The evaluation names the model gaps so they are not rediscovered later: the `P8-T06` queue counter is keyed on date alone while antrean numbers are per-poli (`P14-T01` splits it, keeping the clinic-wide roll as the physical ticket); `AppointmentSession` already matches an HFIS shift with a quota, so a Mobile JKN booking lands as a session join rather than a new appointment concept; the `P7-T06`/`P7-T07` sealed-NIK blind index gives `pasien baru` dedupe-before-create for free, but a BPJS-originated write has no human actor, so the phase needs a system-actor/provenance convention — which doubles as the flag that stops the outbox from re-publishing a Mobile JKN booking back to BPJS as a walk-in; and HMS records no "patient called" event, so whether the FKTP flavour wants FKRTL's task-ID vocabulary decides whether that is a UX change or an approximation. HFIS is reconciled and reported, never synced. Whichever way `P14-T02` resolves the open protocol questions, the outbound half reuses the D-022 codec and HMAC builder unchanged — only the `X-Authorization` header (PCare's `kdAplikasi` login) drops away.

## D-024: The Antrean Spike Stays Open Until Credentials Exist (P14-T02)

- **Status:** **Proposed — blocked on facility credentials.** This ADR is deliberately unfinished. It becomes Accepted when `P14-T02` answers the questions registered in [bpjs-antrean-spike.md](./bpjs-antrean-spike.md) §2, and it is updated in place rather than superseded.
- **Amended (P14-T03 shipped early).** The "Consequence" below said Phase 14 pauses after `P14-T01` and that `P14-T03` onward stay unstarted. `P14-T03` was subsequently built anyway, deliberately, with the credentials still unissued and every question in §2 still open. The reasoning below is not retracted and the status does not change — the spike is still what closes this ADR, and no fixture recorded from a real response exists. What changed is that the hypotheses now live in labelled code instead of prose, so the spike's protocol questions become a test-connection call against a running adapter rather than a blank to fill; [bpjs-antrean-spike.md](./bpjs-antrean-spike.md) §3.1 maps each question to the file that changes if it resolves against us. The gate that still stands unamended is `P14-T04`: Q4 and Q6 are a token scheme and a source-IP allowlist on a public write surface, and a guessed guard there is worse than no code.
- **Amended again (P14-T04 shipped, dark).** The amendment above named `P14-T04` as the gate that still stood. It has now also been built, with Q4, Q5 and Q6 still open — but not in the way that amendment refused. The objection was never "do not write the code", it was _"a guessed guard on a public write path is worse than no code"_, and what makes those two different is whether the path is reachable. It is not: the inbound surface refuses every request, before parsing and before any domain call, unless an operator has configured a source-IP allowlist **and** BPJS's inbound credential pair exist in `BpjsAntreanConfig`. Neither is defaultable and neither can be guessed, because both are values BPJS issues per facility. So the merged state of the repository has no public write path on any deployment, and acquiring one requires the same two facts that would close Q4 and Q6. What is genuinely staged on hypotheses is the _protocol_: the token header, the endpoint paths, the field names, the `metaData` casing. What is not staged is the security model — allowlist before token, token before quota, no HMS identity in the token, a reserved system actor with six enumerated grants, audit on refusals as well as successes. Those hold whatever the spike answers. The status of this ADR does not change: the spike still closes it, and no fixture from a real response exists.
- **Decision:** Do **not** write the `P14-T02` ADR from the reference implementations. Stage the spike instead: record what must be obtained from the branch office, register every open protocol question with its current hypothesis and evidence standing, name what each answer unblocks, and state plainly what must not be built before the answers exist. `P14-T03` onward stay unstarted.
- **Why:** `P14-T02`'s output is an ADR plus recorded fixtures, and both require the pilot clinic's Antrean-service credentials, which BPJS issues per facility through its branch office under a signed pakta integritas. The credentials do not exist. An ADR written now would be assembled from the same community sources D-022 used, but without D-022's saving grace: there, two independent implementations agreed exactly and an openssl cross-check confirmed the codec byte-for-byte, so the document recorded verified facts with one open item. Here the FKTP material is thinner and mixes freely with the better-documented FKRTL flavour, and the largest open question — whether FKTP uses FKRTL's task-ID vocabulary or only `panggil` — changes how many lifecycle events HMS must emit and whether the registration lifecycle needs a "patient called" event it does not have today. An ADR is a record of decisions taken on evidence; one written to fill the slot would read as authoritative to the next reader and be guesswork, and the evaluation already made the narrower version of this point about fixtures: _"Fixtures test our reading of the spec, not the spec."_
- **Consequence:** Phase 14 is paused after `P14-T01` (per-poli queue numbering, shipped — it was always the only task with no external dependency). The spike document is the deliverable in the meantime, and it is written so that whoever runs the real spike does discovery, not rediscovery: the credential intake is a checklist, each question names the task it blocks, and the fixture list says record-from-real-responses with a redaction rule. Two answers are flagged as potentially schedule-changing rather than merely informational — if task IDs apply, the registration-lifecycle event becomes its own task instead of being smuggled into `P14-T05`; if HFIS and PCare poli/doctor codes diverge, HFIS-scoped mapping columns must be scheduled before `P14-T03`. Phase 15 is explicitly independent of Phase 14 and remains available to run in the meantime.

## D-025: Entitlement Management Is Control-Plane, Not Clinic-Portal (IMP-6 … IMP-9)

- **Status:** Accepted
- **Decision:** Keep entitlement **enforcement** in the tenant database, where `IMP-6` … `IMP-8` put it. Place entitlement **management** — the screen, and the people who use it — in the control plane described in [multi-tenancy.md §1](./multi-tenancy.md). Do **not** add a role above `SUPER_ADMIN`, and do **not** add a Features tab to `/admin/administration`. Until the control plane exists (multi-tenancy.md §10, M0), switching a feature is a documented ops action against `PUT /api/v1/admin/features/:key` with no user interface at all.
- **Why:** Feature entitlements are commercial packaging: per-tenant, vendor-owned, and never changed by the clinic. That is the same category as the tenant registry, and [multi-tenancy.md §6.4](./multi-tenancy.md) has already ruled on where actors of that kind live — _"Platform staff are a separate concept … It must never be a flag on the ordinary user path."_ A `PLATFORM_OWNER` role stacked above `SUPER_ADMIN` is precisely such a flag, and it fails three ways:
  1. **It is not hidden.** Roles live in the tenant's own `roles` table. `GET /rbac/roles` returns it, the `IMP-4` Roles tab lists it, and the permission matrix renders its grants. A clinic admin would see a role they cannot use and ask what it is — the one question the mechanism exists to avoid.
  2. **It is not above anything.** [permissions.guard.ts:78](../../apps/api/src/common/authorization/permissions.guard.ts) hardcodes `SUPER_ADMIN` → `manage:all`. There is no rung above that inside a tenant database, so adding one means a second hardcoded escalation in the guard where there is currently one — and the guard is the file least improved by special cases.
  3. **The tenant database is the clinic's.** Under the per-tenant-database decision, anything stored there is reachable by whoever holds the connection. A vendor-only role stored inside the tenant it is meant to govern is a soft boundary dressed as a hard one.
     Worth recording alongside this: `SUPER_ADMIN` is **not** vendor-only today — `seed.sql` assigns it to `admin@salingjaga.com`, the clinic's own administrator. The separation this ADR assumes does not exist yet in either direction, and §6.4 is what creates it.
- **Consequence:** `IMP-6` … `IMP-8` stand unchanged and no rework is implied. `FeatureGuard` must keep reading the entitlement on the tenant's own connection — moving enforcement to the control plane would put a network hop in front of every guarded request, which is the one thing `IMP-8`'s cache exists to avoid. `IMP-9` is unaffected: `GET /features/availability` is a tenant route answering for the signed-in user, not a management surface. No ticket is filed for a clinic-portal features screen; the interim runbook folds into `IMP-10` instead, so the board carries no row that would build the rejected version. At M0 the entitlement becomes a control-plane table, the tenant row becomes a projection refreshed on write, and `PUT /admin/features/:key` stops being an operator-facing endpoint and becomes the control plane's write path into a tenant. Platform-staff access, whenever it lands, follows §6.4 unchanged — distinct token type, explicit time-boxed impersonation, `TENANT_IMPERSONATION_STARTED` / `_ENDED` written to both the control plane and the clinic's own audit log. Left deliberately open: whether `feature.read:any` and `feature.manage:any` survive in the tenant permission catalog once the control plane owns the write path, or are retired in favour of a platform token — that is decided at M0 with the routing layer in front of it, not now.

## D-026: HTML→PDF Rendering Runs in a Network-Denied Gotenberg Sidecar (P16-T01 Spike)

- **Status:** Accepted
- **Decision:** Render invoice and clinical documents by POSTing self-contained HTML to a **Gotenberg 8 sidecar** on `/forms/chromium/convert/html`, and reach it through an internal port at `apps/api/src/common/pdf/` (`PdfRendererService` abstract class, `GotenbergPdfRendererService` adapter, `PdfModule`) that mirrors `ObjectStorageService`. The container is pinned to `gotenberg/gotenberg:8.36.0`, sits behind the `pdf` compose profile with **no published port** on an `internal: true` Docker network with **no gateway**, runs with Chromium's own outbound filtering denying both private and public IPs, and has the LibreOffice and PDF-engine routes disabled. Reject Puppeteer-in-the-API-image, `@react-pdf/renderer`/`pdfmake`, and `wkhtmltopdf`.
- **Why:** The template is authored as HTML in a WYSIWYG editor, so fidelity means a real browser engine, and that narrows the field to Chromium in-process or Chromium in a sidecar. The sidecar wins on the property that matters here: **Chromium is the largest untrusted-input parser this product will ever hold, and a renderer bug must not land in the process holding the database connection and the application's credentials.** The measurements below then removed the two objections the PRD raised against it (§R-1: ops cost; latency). Everything in the table was measured in this spike, not estimated.

### What was measured

Host: Apple Silicon, Docker Desktop 28.0.1, `gotenberg/gotenberg:8.36.0` (Chromium m151, `Producer: Skia/PDF m151`). Document under test: a 3-page A4 invoice — header block with a `data:` URI logo, 70 line items, totals, _terbilang_ line, 7.7 KB of self-contained HTML in, 39.8 KB of PDF out.

| Measure                          | Result                                                                |
| -------------------------------- | --------------------------------------------------------------------- |
| Image — registry download        | 690 MB (arm64) / 698 MB (amd64), 18 layers                            |
| Image — unpacked on disk         | 2.45 GB                                                               |
| Cold start → `/health` answering | 229 / 233 / 332 ms over three fresh containers                        |
| Cold start → first PDF in hand   | 561 / 625 / 811 ms (Chromium launches lazily on the first conversion) |
| Warm render, serial (n=30)       | p50 **75 ms**, p90 80 ms, p95 **89 ms**, max 120 ms                   |
| Warm render, 6 concurrent (n=36) | p50 228 ms, p95 456 ms, max 503 ms                                    |
| Resident memory, Chromium warm   | ~285 MiB                                                              |

The PRD's §8 budget for a PDF download is 5 s. The p95 is 89 ms warm and under a second from a container that does not exist yet, so latency is not a design constraint on `P16-T06` — it is free headroom. Six concurrent renders is Chromium's own `--chromium-max-concurrency` ceiling; past it Gotenberg queues rather than degrading, which is the correct failure shape for a burst of cashiers hitting _Download_.

### Outbound denial, proven rather than asserted

NFR-SEC-03 says the renderer must not be able to fetch a remote reference a template retained. That was tested as an A/B against a tracking HTTP server, not read off the documentation:

| Configuration                                                             | Remote `<link>` + `<img>` in the template                                                                             | Render       |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------ |
| Routable bridge, no deny flags (**control**)                              | **2 hits** — both the stylesheet and the image were fetched                                                           | 200          |
| Routable bridge, `--chromium-deny-private-ips --chromium-deny-public-ips` | **0 hits**                                                                                                            | 200, 3 pages |
| Compose `internal: true` network                                          | **0 hits**; container has no default route, `curl` to a public IP fails with connect-refused and DNS does not resolve | 200, 3 pages |

The middle row is the one that isolates the cause. That container was started with `--add-host host.docker.internal:host-gateway` and a shell `curl` from inside it reached the tracker and was recorded — so the host was reachable, and Chromium still fetched nothing. Both layers are kept: Docker's `internal` network is the guarantee, and Chromium's filtering is what preserves the posture if a deployment ever puts this container on a routable network by mistake.

`gotenberg-pdf-renderer.integration.spec.ts` carries the A/B as a test. It passes against the hardened container and **fails** against an unhardened one, which is the only reason to trust it.

### Findings that change downstream work

1. **Chromium emits `%PDF-1.4`, not 1.7.** Skia's PDF backend has always written a 1.4 header. Nothing in E1 depends on the version, but `P16-T37` (password protection) does: PDF 1.4 encryption is RC4/40–128-bit, so that task must apply AES-256 encryption in the API with its own library and rewrite the version marker, not ask the renderer for it. Gotenberg has no encryption route at all, so this was never going to be a form field.
2. **`failOnConsoleExceptions=true` does not trip on blocked sub-resources.** A denied stylesheet or image is a network failure, not a console exception, so the adapter can keep the flag on — a template whose _script_ throws still fails loudly — while a stray remote reference still renders. That is what makes the PRD's stated behaviour ("renders empty + a warning, never a failed PDF") achievable with the strict flag set.
3. **The entry point is identified by filename.** Gotenberg renders the multipart part named `index.html` and treats every other part as an asset; a part named anything else produces `400 form file 'index.html' is required`. The adapter pins the name and the unit spec asserts it.
4. **No published port means a host-run API cannot render.** This is the posture working, not a misconfiguration, and it is the one ergonomic cost of the decision: the everyday `pnpm dev` loop on the host has no renderer, so PDF work is done with the API itself in compose (`pnpm docker:dev:pdf` alongside `pnpm docker:dev:start`), and the integration suite is opt-in against a throwaway container. Publishing the port to make the host loop nicer would put the renderer on the developer's LAN, which is precisely the trade this ADR refuses.
5. **The image is large and it is Chromium plus LibreOffice.** 690 MB pulled, 2.45 GB unpacked. HMS uses exactly one of Gotenberg's routes, so LibreOffice and PDF-engine routes are disabled — the two biggest parsers in the image are unreachable from any code path we have. That does mean PDF/A conversion is not available without re-enabling `pdfengines`; nothing in Phase 16 asks for it, and re-enabling is one flag if that changes.

- **Consequence:** `P16-T06` builds the render service on `PdfRendererService` unchanged — resolve variables, produce self-contained HTML, call `render`, checksum and store the bytes — and inherits the fail-closed contract: an unconfigured, unreachable, slow, or non-PDF-answering renderer is a `ServiceUnavailableException` carrying a status but never the upstream body, because Gotenberg's error text can quote the document it was handed and those documents are invoices and clinical letters. `InvoiceDocument.status = FAILED` is written from that, and recording a payment is never blocked by it. The **self-contained HTML rule is now load-bearing rather than stylistic**: `P16-T05`'s sanitiser and `P16-T12`'s publish-time validation are what keep remote references out of templates, and this container is what makes a leak harmless rather than a data-exfiltration path. Deployment manifests must reproduce **both** halves of the isolation — a Kubernetes NetworkPolicy denying egress plus the same Chromium flags — or the guarantee is compose-only; the pinned patch tag is part of the decision, because Chromium decides line and page breaks and a floating `:8` would re-paginate already-issued invoices on an unrelated pull, which is the exact thing snapshotting an issued document exists to prevent. Rollback stays as the PRD described it: remove the container and PDF requests fail closed with a clear error while billing continues.

## D-027: Every Delivered Document Is a Password-Protected PDF, Locked in the API (P16-T37)

- **Status:** Accepted
- **Decision:** A document delivered to a patient over WhatsApp or email travels as an **attachment** by default on both channels, and every attachment is a PDF **encrypted with a user password before it leaves the system**. Encryption is AES-256 (`/V 5 /R 6`), applied in the API by `PdfEncryptionService` (`apps/api/src/common/pdf/`) between render and transport — never by the renderer, which emits PDF 1.4 and has no encryption route (D-026, finding 1). The default password is the patient's **date of birth as `DDMMYYYY`**; the scheme is configurable per deployment through `DELIVERY_PDF_PASSWORD_SOURCE` (`DOB_DDMMYYYY`, `DOB_YYYYMMDD`, `MRN`), which on the single-tenant build is per clinic (FR-E4-06). The message that carries the file **names the scheme and never the value** — "open with your date of birth, DDMMYYYY" (FR-E4-08). The password is recomputed at send time and stored nowhere; the delivery row records only `passwordSource`. A patient with no date of birth on file cannot receive a DOB-locked document: the send is refused with a message naming the missing field and the record to complete (FR-E4-07).
- **Why:** The password moves the protection from _"can we take it back"_ to _"can the wrong recipient open it"_, which is the failure that actually happens — a mistyped digit or a wrong address, not a determined attacker. A plain attachment is readable by whoever received it by mistake; a revocable link needs data, a browser and a support call, and a patient who wants to keep their receipt for reimbursement loses it when the link expires. A locked attachment works offline, keeps forever, and is inert to a stranger. The date of birth is the default because it is something the patient knows without being told and a misdialled number's owner does not. **It is not a secret in the cryptographic sense** — someone who knows the patient can guess it — and this record says so rather than implying otherwise: it is the right control for misdelivery and the wrong one for a targeted attack, and a clinic that wants the latter configures a different source.
- **Consequence:** `ProtectDeliveryDocumentService` (`apps/api/src/modules/document-delivery/`) is the one call the delivery worker (`P16-T25`/`T26`) and clinical-document release (`P16-T40`) make between the rendered bytes and the transport; it returns the locked bytes and the scheme, and nothing that carries the password survives the call. The owner password is fresh randomness per file and discarded, so nobody can lift the restrictions from a delivered copy; the clinic re-issues from its own unlocked object in storage, never from a delivered file. The round-trip is asserted in CI against a real PDF reader: the output demands the password, opens with the correct one, refuses the wrong one, and the header is raised from Chromium's 1.4 to 1.7 so the file is self-consistent. Link delivery (FR-E4-11) remains a per-channel option for a clinic that prefers it and is unaffected by this decision.

## D-028: One Delivery Table for Invoices and Clinical Documents (P16-T25)

- **Status:** Accepted
- **Decision:** A document delivered to a patient is one row in **`document_deliveries`** whatever the document is — an invoice's rendered snapshot today (`P16-T25`), a released clinical document under `P16-T40`. The row names exactly one subject (`invoice_id` + `invoice_document_id`, or `document_id`), enforced by a CHECK in the migration, the same shape `invoices` uses for encounter-or-admission. The PRD's `InvoiceDelivery` / `InvoiceDeliveryLink` are this table and `document_delivery_links`; the API paths the PRD names are kept (`/invoices/:id/deliveries` for the request and the timeline), and the per-row actions live under `/deliveries/:id/…` because a retry is a retry whichever document is inside. The pipeline lives in `apps/api/src/modules/document-delivery/`, which imports `BillingModule` for facts about the bill and never the other way round.
- **Why:** The consent gate (`P16-T24`), the password lock (`P16-T37`), the lease-claimed worker (`P16-T26`), the daily cap, the timeline and the audit verbs are the same whichever document is being sent. Two tables would mean two workers, two retry paths and two timelines that must never drift — and the first divergence would be a clinical document that retries differently from a bill for no reason anyone chose. One table with a subject XOR costs one CHECK and two nullable columns, and makes `P16-T40` a trigger on release rather than a second copy of the pipeline.
- **Consequence:** Every read and write in `DocumentDeliveryRepository` selects the row explicitly; there is no destination column to leak, only `destination_masked`. `P16-T40` adds a `document_id` branch to the send path and nothing to the schema. The link table cascades from its delivery; the delivery restricts every subject it names, because a delivery row is evidence of what left the building. The public link route (`GET /delivery-links/:token`) is the one unauthenticated surface in the epic: every failure is the same 404, and both counters — per address, per token — are in-memory and per replica on purpose, because the limit exists to make enumeration expensive, not to be an exact quota.

## D-029: The Drafter Names Who Approves, Per Document (P16-T29, confirmed P16-T21)

- **Status:** Accepted
- **Decision:** Approval routing is **per document and per round**: the drafter names the approvers at the moment they submit, and the panel is frozen into the round with the content (`document_approval_approvers`). There is no approver registry, no per-division routing table and no approver role. A document type may carry _default_ approvers to pre-fill the picker (FR-E5-38), and the drafter is free to change them. Deciding requires two independent conditions — being named on the round, and holding `document-approval.decide:any` — and neither is sufficient alone (FR-E5-13).
- **Why:** The clinic this is built for has one site and a handful of staff, and who should sign a particular consent form is a fact about that form, not about an org chart. A routing table would have to be maintained by somebody, would be wrong the first time a person was on leave, and would answer a question the drafter already knows the answer to. Freezing the panel into the round is what stops the answer changing under the approvers after they were asked. The permission is separate from the naming because the two failures are different: naming somebody who cannot decide is a mistake the drafter can fix, and granting decide to somebody nobody named must not by itself let them sign anything.
- **Consequence:** `DocumentApprovalService` enforces both halves and refuses a panel that could only ever self-approve at _submit_ time rather than at approve time, so the drafter learns while they can still fix it (§7.5.10). No role was seeded for approvers (OQ-1). The cost is that a drafter can name somebody who is on leave, which is why a round carries an optional deadline that drives reminders and an overdue flag — and never a decision (FR-E5-28) — and why withdraw is always available to the drafter (R-15).
- **Numbering note:** this decision was cited as "D-028" in `packages/shared-types/src/document-approval/schemas.ts` while D-028 was already taken by the delivery-table decision above. `P16-T21` found the collision and assigned this number; the citation is corrected.

## D-030: An Inpatient Encounter Is Reported at Discharge, Not at Close (P10-T09)

- **Status:** Accepted
- **Decision:** The SATUSEHAT outbox has **two producers**. An encounter with no admission, or with one already discharged or cancelled, enqueues at the FINISHED close in `EncounterRepository.closeEncounter` as before. An encounter whose patient is **still admitted** enqueues nothing there; the row is written inside `AdmissionFlowRepository.dischargeAdmission` instead, in that transaction. The Encounter is then reported with `class: IMP`, a `period` running check-in to discharge, an `in-progress` status-history entry spanning admission to discharge, and a `hospitalization` element.
- **Why:** `mapEncounter` hard-coded `class: AMB`. With admissions live, an admitted patient's visit was reported as ambulatory — not a failed submission but a **wrong** one, which no monitor will ever flag. The IG's rawat-inap use case requires `IMP`, the stay's period and a `hospitalization` element, and none of those are known while the patient is still in a bed. Sending at close would mean either reporting an episode that has not ended or issuing a correction later; moving the enqueue to the event that actually ends the episode avoids both. Writing another module's table is the same trade the close path already makes, for the same reason: the outbox guarantee is that the event and its queue entry commit or roll back together, and an after-commit enqueue reintroduces the silent-miss window the outbox exists to remove.
- **Consequence:** Two orderings exist and both are safe. Close-then-discharge enqueues at discharge; discharge-then-close (the doctor who finishes the chart late) enqueues at close, which by then sees a discharged admission and reports `IMP` normally. The discharge-side insert is an upsert on the unique `encounter_id`, so neither ordering can queue a visit twice. A cancelled admission is a stay that never happened and leaves the visit ambulatory. `dischargeDisposition` is sent as `home` for every stay: the clinic records no disposition anywhere, and a column for it belongs to whichever ticket gives staff somewhere to enter one — not to a mapper that would be inventing the value. Ward-level Locations stay out of scope: only the facility `Location` is registered on the platform, so `location` is unchanged. `EMER` also stays out until a registration type records an emergency visit; deriving one from a timestamp would be a fiction.

## D-032: The Flat Doctor Licence Number Is the STR; SIP Belongs in the Typed Licence List (P19-T13)

- **Status:** Accepted (research outcome — UI relabel and guidance only, no schema or data change)
- **Decision:** `DoctorProfile.licenseNumber` — the flat, required, `@unique` string collected once when a doctor is created — **is the doctor's STR number**, and the UI is relabelled to say so ("STR Number" / "Nomor STR") in the create form, the directory table column and the profile card. **SIP numbers belong in the typed `licenses[]` list**, one row per practice location, where the existing `type ∈ {STR, SIP}` / `issuedAt` / `expiresAt` shape already fits them. The Zod contract is **left exactly as it is** (`z.string().trim().min(3).max(64)`): the research below does not fix a format tightly enough to justify a pattern. Nothing moves in the database and no column is added, renamed or dropped.
- **Why:** Three properties of the two documents decide it, and they all point the same way.

  **1. A doctor has exactly one STR and up to three SIPs.** The STR (Surat Tanda Registrasi) is issued by the Konsil Kesehatan Indonesia, is per person, and is now lifetime — the Konsil's own FAQ states the requirement plainly: _"STR yang digunakan yaitu STR Aktif dan berlaku seumur hidup."_ ([kki.go.id/faq](https://www.kki.go.id/faq)). The SIP (Surat Izin Praktik) is the opposite on every axis: PP 28/2024 Pasal 682 ayat (2) fixes _"satu SIP hanya berlaku untuk satu tempat praktik"_, and a doctor may hold at most three, one per site ([kemkes.go.id](https://kemkes.go.id/eng/dokter-tetap-bisa-praktik-di-tiga-tempat-ini-syaratnya)). A column with a `@unique` constraint and exactly one value per doctor is an STR-shaped column. It is not a SIP-shaped column, and the old `SIP-2026-0001` placeholder was asking the desk to type a value the column cannot correctly hold for a doctor who practises anywhere else.

  **2. The SIP has no national numbering convention, so it cannot be validated centrally.** SIPs are issued locally — in DKI Jakarta by the Dinas Penanaman Modal dan PTSP, with a five-year validity ([jakarta.go.id](https://www.jakarta.go.id/surat-izin-praktik)) — and each issuing office numbers its own letters. Neither that page nor any other primary source consulted publishes a format. A SIP number is therefore free text that only its issuing office can interpret, which is another reason it belongs in a typed list beside its issue and expiry dates rather than in an identity column.

  **3. The STR number format is _nearly_ fixed, but not from a source we could read.** The Konsil published, on its own site, that from 4 September 2023 the STR number changed from sixteen digits to two letters followed by fourteen digits, and that numbers in the old format remain valid and are converted gradually ([kki.go.id blog](https://kki.go.id/blog/read/proses-penerbitan-surat-tanda-regsitrasi-str-dokter-dan-dokter-gigi-terintegrasi-dengan-sistem-informasisumber-daya-manusia-kesehatan-si-sdmk)). **That page could not be read directly.** Every path on `kki.go.id` except `/faq` answered HTTP 500 on 10 September 2026, from three different clients, and the page has no Wayback snapshot; the wording above is known only through a search engine's quotation of it. A Kemenkes FAQ separately describes the lifetime STR as sixteen alphanumeric characters, which agrees. Two independent readings agreeing is normally enough — but a regex is a rule that rejects a real doctor's real number, and by the Sprint 22 lesson a format is confirmed from the document or it is not confirmed. **So: no pattern.** `.trim()` is already on the field and already does the one thing that is unambiguously right (a number pasted out of SATUSEHAT SDMK carries whitespace, and `@unique` treats `" AB…"` and `"AB…"` as different doctors). The guidance copy states the shape so the human at the desk can check it; the validator does not enforce it.

  **4. SATUSEHAT cannot prefill the STR today.** The ticket assumed a Practitioner lookup by NIK returns the STR via `Practitioner.identifier`. Neither the platform's Practitioner resource page, the FHIR R4 IG developer page, nor the onboarding API catalogue publishes a populated Practitioner response or names an STR identifier system; the only identifier documented for practitioner search is NIK, `https://fhir.kemkes.go.id/id/nik` ([IG](https://simplifier.net/guide/SATUSEHAT-FHIR-R4-Implementation-Guide/Home/Developer/Practitioner.page.md?version=current), [onboarding](https://satusehat.kemkes.go.id/platform/docs/id/api-catalogue/onboardings/apis/practitioner/)). Our own linking code matches on NIK alone and stores no STR from the response. Prefill and verification are therefore a **follow-up spike against the live sandbox**, not something to claim in a tooltip.

- **Consequence:** The label changes in three places; the data does not. Any doctor row created before this decision may hold a SIP number in a column now labelled "STR Number", and nothing in this change detects or corrects that — a backfill (read the flat value, decide STR or SIP, move the SIP ones into `licenses[]`) is a separate ticket, and until it runs the directory's STR column is only as truthful as what was typed. The typed `licenses[]` list stays the system of record for expiry: STR no longer expires, so the licence-expiry worker and the out-of-licence page remain meaningful for SIP rows, which is what they mostly watch already. Because the Zod schema is untouched, this decision produces no OpenAPI change and no client regeneration. If the Konsil site comes back up and the numbering announcement can be read from the source, a `^[A-Z]{2}\d{14}$|^\d{16}$` pattern becomes defensible — but it would still need a migration plan for stored values that match neither, so it is a ticket of its own rather than a one-line edit.

## D-033: Clinical Record Content Is for the Clinicians Who Examine the Patient (P22-T01)

- **Status:** Rule **Accepted** (product owner, 11 September 2026). The resolution of each edge case below is **Proposed** until confirmed in review, and P22-T02 is split into enforcement tickets only after that confirmation.
- **Number:** D-033 was reserved for this ticket when it was filed, ahead of D-034 (P24-T02) and D-035 (P21-T09), so it sits before them here. For the numbering collisions between the two decision files, see the preamble above and D-027 in `docs/MVP/decisions.md`.
- **Decision:** **The content of a patient's clinical record is accessed only by clinicians who examine that patient.** The clinician roles are `DOCTOR` and `MIDWIFE` (D-034, P24-T02, FR-MW-08), and a `NURSE` role would join them if one is introduced. Wherever this record says "doctor" about access, it means any clinician. Everyone else in the clinic reaches clinical content only through two narrow openings that are defined here and nowhere else: **task access**, where a health worker reads the one order they are carrying out, and **billing lines**, where the cashier sees the invoice descriptions they charge for. Patients reading their own record are unaffected.

  **What counts as the clinical record:** SOAP notes and clinical impressions; diagnoses; procedures; vital signs; allergies; immunizations; prescriptions and dispensing; lab orders, specimens and results; clinical documents (`DocumentPurpose.PATIENT_CLINICAL`: lab results, referral letters, scanned consent forms); and the content of chat messages about a patient's health. **What does not count:** identity and national identifiers (governed separately by the audited reveal routes), demographics, appointments and sessions, queue position, registration status, and payment status. A screen or permission that touches only the second list needs nothing from this record.

- **Legal basis, and what it does and does not require.** The source is Peraturan Menteri Kesehatan Nomor 24 Tahun 2022 tentang Rekam Medis, ditetapkan and diundangkan 31 August 2022, Berita Negara Republik Indonesia Tahun 2022 Nomor 829. The article text below was extracted on 13 September 2026 from the official PDF on `peraturan.bpk.go.id`. It was **not** taken from secondary summaries, and the reason matters: the summaries cite the wrong articles (Pasal 10, 18 and 19), a model-written digest of the same PDF invented a different date and gazette number, and one reproduction site now serves a gambling page. The operative text is:

  > **Pasal 30 (1)** Dalam rangka keamanan dan perlindungan data Rekam Medis Elektronik, pimpinan Fasilitas Pelayanan Kesehatan memberikan hak akses kepada Tenaga Kesehatan dan/atau tenaga lain di Fasilitas Pelayanan Kesehatan.
  > **(3)** Hak akses sebagaimana dimaksud pada ayat (1) terdiri atas hak untuk: a. penginputan data; b. perbaikan data; dan c. melihat data.
  > **(8)** Melihat data sebagaimana dimaksud pada ayat (3) huruf c merupakan kegiatan yang dilakukan oleh tenaga internal Fasilitas Pelayanan Kesehatan untuk mendapatkan informasi terkait data di dalam Rekam Medis Elektronik untuk keperluan pelayanan atau administrasi.
  > **(9)** Hak akses sebagaimana dimaksud pada ayat (1) diatur dalam kebijakan pimpinan Fasilitas Pelayanan Kesehatan dengan memperhatikan prinsip keamanan data dan informasi sebagaimana dimaksud dalam Pasal 29.
  > **Pasal 32 (1)** Isi Rekam Medis wajib dijaga kerahasiaannya oleh semua pihak yang terlibat dalam pelayanan kesehatan di Fasilitas Pelayanan Kesehatan walaupun Pasien telah meninggal dunia. **(2)** Pihak sebagaimana dimaksud pada ayat (1) meliputi: a. Tenaga Kesehatan pemberi pelayanan kesehatan, dokter dan dokter gigi, dan/atau Tenaga Kesehatan lain yang memiliki akses terhadap data dan informasi kesehatan Pasien; b. pimpinan Fasilitas Pelayanan Kesehatan; c. tenaga yang berkaitan dengan pembiayaan pelayanan kesehatan; …
  > **Pasal 33 (3)** Pembukaan isi Rekam Medis sebagaimana dimaksud pada ayat (1) dilakukan terbatas sesuai dengan kebutuhan.
  > **Pasal 34 (1)** Pembukaan isi Rekam Medis atas persetujuan Pasien … dilakukan untuk: a. kepentingan pemeliharaan kesehatan, pengobatan, penyembuhan, dan perawatan Pasien; b. permintaan Pasien sendiri; dan/atau c. keperluan administrasi, pembayaran asuransi atau jaminan pembiayaan kesehatan.

  Three consequences follow, and the rest of this record depends on them. **First, the regulation does not require doctor-only access.** It expects the facility to grant access to health workers _and other staff_ (Pasal 30(1)), including viewing for administrative purposes (Pasal 30(8)). So this rule is a facility policy that is **stricter than the law**, which Pasal 30(9) explicitly allows the facility's leadership to set. It must not be described as a legal mandate. **Second,** access "terbatas sesuai dengan kebutuhan" (Pasal 33(3)) is the legal anchor for the need-to-know scoping below. **Third,** billing staff are named among those bound to confidentiality (Pasal 32(2)(c)), and administration and payment are named purposes (Pasal 34(1)(c)), so invoice lines have direct footing. What remains open is a legal _opinion_, not the text: nobody qualified has yet reviewed whether this policy needs to be written up in the clinic's standar prosedur operasional (Pasal 30(2)). Record that review in P22-T02 before enforcement ships.

## D-035: Changing a NIK Clears the SATUSEHAT Link and Requires Relinking (P21-T09)

- **Status:** Accepted (bug fix — behaviour change on two update paths, no schema change)
- **Number:** D-033 is reserved by P22-T01 (clinical record access) and D-034 by P24-T02 (a midwife is a profession), both filed before this one, so this record takes **D-035**. On the numbering collisions between the two decision files, see the note under D-027 in `docs/MVP/decisions.md`.
- **Decision:** When a doctor's or a patient's **NIK changes**, the SATUSEHAT link derived from it is **cleared in the same update**, and the record must be linked again before its next submission. The alternative — refusing a NIK change while a link exists — is rejected. Comparison is by **blind index**, so saving the same NIK again is not a change and does not unlink. Clearing to `null` is a change like any other and also unlinks. Encounters already submitted keep the reference they were sent with; this governs only what is sent next.
- **Why:** The IHS number is not an attribute of the record we hold — it is the answer to one question, _"which national record does this NIK belong to?"_. Once the NIK changes, the stored answer is an answer to a question nobody asked, and every later bundle quietly asserts that the person in front of us is the person that old NIK identified.

  **Refusing the change is worse than clearing it.** The overwhelmingly common reason a NIK changes is that it was typed wrong at the counter. Refusing the edit while linked means the only way to correct a typo is to leave the wrong NIK in place — or to have someone edit the database — and in the meantime every visit continues reporting to a stranger's national record. Refusing protects the link at the expense of the patient.

  **Clearing is also the honest reading of what we know.** After a NIK correction we genuinely do not know the right IHS number; the worker resolves it by lookup on the next submission (doctors and patients both), so relinking is automatic in the ordinary case and needs no operator action at all. Where it is not automatic — a NIK matching several practitioners — that is exactly the case P21-T08 exists to answer, and leaving the record visibly unlinked is what routes the operator there.

  **Blind index, not ciphertext, decides whether it changed.** The identifier columns are re-encrypted on every write, so ciphertext differs even when the value does not; comparing it would unlink on every unrelated profile edit. The searchable index is deterministic for a given key version, which is what makes "same NIK saved again" distinguishable from "different NIK".

  **Amended 2026-09-20 (P24-T13, FR-NB-05): a newborn's first NIK does not unlink her.** One case falls outside the reasoning above, and it is the case this rule would get exactly backwards. A baby registered under her mother (`motherPatientId` set, P24-T10) was never resolved by NIK at all: she was **created** on the master patient index under her mother's `nik-ibu`, and the IHS number the platform assigned is hers, not an answer to a question about an identifier. When her own NIK arrives weeks later, that is new information about the same person, so the link is **kept** and the identifier is sent upstream as a `PATCH /Patient/{id}` instead — which is what the platform's own newborn page says to do. The exemption is narrow by construction: only a **first** NIK (the stored blind index is null), and only for a patient with a mother on record. A newborn whose NIK is later corrected unlinks like anybody else, because by then the link is an answer to a NIK. The decision is one pure function, `resolveSatusehatLinkNikEffect`, so the exemption is testable rather than a condition inside a transaction.

  The patch is **not retried** on a timeout: it appends an identifier (`add /identifier/-`), so replaying one that in fact landed would give the baby her NIK twice. An unconfirmed patch is surfaced to the admin instead. A Dukcapil refusal is likewise shown and **never rolls the local write back** — the family brought a real identifier to the counter, and the platform disagreeing about a name is not a reason to lose it. Both outcomes audit `SATUSEHAT_PATIENT_NIK_PATCHED` with the outcome and never the NIK.

  **The patient side was the more dangerous half.** `updatePatientSchema` accepts `nik: null`, so a patient's NIK could be cleared entirely while `satusehat_patient_id_ciphertext` kept pointing at a national record — and unlike a doctor, a patient's submissions carry their clinical history.

- **Consequence:** Two repository update paths clear a link they previously left alone, so an operator who corrects a NIK now sees the record as not linked, with the Link action available. That is a visible behaviour change on a screen nobody was watching for it, which is why it is a decision record and not just a patch. The unlink is audited (`SATUSEHAT_LINK_CLEARED`) with the reason and never with the NIK itself. Rows whose NIK was already changed **before** this shipped still hold a stale link and this change does not detect them: a sweep would have to compare each stored IHS number against a fresh lookup, which is a ticket of its own and, on the patient side, an audited decrypt of every identifier. Until then, a record linked before today is only as correct as its NIK history.

## D-036: Midwife Authority Kinds Stay, Their Legal Basis and Evidence Move to PP 28/2024 and Permenkes 13/2025 (P25-T01)

- **Status:** Accepted (research outcome — changes the E6 record shape before P25-T02 is built, no code on this ticket)
- **Number:** D-035 is the last entry in this file. D-numbers collide with `docs/MVP/decisions.md` (see the note under D-027 there), so cite this record as `docs/post-mvp/decisions.md` D-036.
- **Decision:** The five `DoctorAuthority` kinds of FR-AUTH-01 — `IUD_IMPLANT`, `MTBS`, `PROGRAM_IMMUNIZATION`, `INTEGRATED_ANC`, `NO_OTHER_WORKER` — are **kept with their names and meanings**. What changes: (1) the record's legal basis is PP 28/2024 Pasal 744 and Permenkes 13/2025 Pasal 185–187 (programme and no-other-worker authority) and PP 28/2024 Pasal 742(3)–(4) (training-added competence on the STR), not Permenkes 28/2017 Pasal 23–26; (2) the grant evidence is **one of** a dinas kesehatan penetapan, a government penugasan letter, or the STR annotation of the added competence, with the training certificate always required, and the validity period is the one the government set — never open-ended; (3) the doctor's mandate record (FR-AUTH-04) gains a second form, **`DELEGATION`** (PP 28/2024 Pasal 745(3), Permenkes 13/2025 Pasal 184), next to `MANDATE`, with the rules that both are written, both are reported back to the doctor, and a delegation is valid only while the doctor is absent for one to three months. The alternative — renaming the kinds after the new regulation's vocabulary ("keadaan tertentu: program pemerintah", "ketiadaan tenaga") — is rejected.
- **Why:** Permenkes 28/2017 was revoked by Permenkes 13/2025 Pasal 309 huruf cc, so a record whose help text and validation cite "Pasal 23 ayat (5)" would cite a dead provision from its first day. But the same regulation's Pasal 305(1) keeps the per-profession practice Permenkes as the reference for a health worker's authority until a standar profesi under Pasal 174(3) is stipulated by the Minister, and no such standard for midwives could be found on a government site on 2026-09-15. So the **list of actions** a midwife needs an authority for is still the Permenkes 28/2017 Pasal 25 list, and the kinds that name those actions are still correct. What the new framework changed is **how** the authority is granted (penugasan after training, for a set period, or a competence added to the STR) and **who** carries responsibility under a pelimpahan (a mandate leaves it with the doctor; a delegation moves it to the midwife). Renaming the kinds would break nothing legal and would cost every later ticket that already references them; changing the evidence fields costs one migration now and avoids refusing a midwife whose grant is an STR annotation rather than a decree.
- **Consequence:** P25-T02 models `grantKind` (`DINAS_PENETAPAN`, `GOVERNMENT_PENUGASAN`, `STR_ANNOTATION`) with a reference and date, keeps the training certificate mandatory, and requires `validTo`. P25-T05 models `MANDATE` and `DELEGATION` on the mandate record, drops the "same FKTP" and "never continuous" checks to policy warnings, and shows the responsible clinician per form. When a Pasal 174(3) standar profesi bidan is stipulated, this decision is reviewed against it: if the standard enumerates the programme actions differently, the kinds change then, with a data migration, and this record is superseded. The research and the quoted pasal are in `docs/ops/midwife-practice-research.md` §1.
- **Built (P25-T05, 2026-09-20):** `DoctorMandate` carries `kind`, the mandating doctor, the delegated ICD-9-CM codes, a required window and a required written instruction in object storage; `procedures.mandate_id` records which pelimpahan an action was taken under, and the encounter card names it ("Di bawah mandat dr. …"). The procedure gate asks in one order — her own authority, then a live mandate naming the code, then refuse — so an action she may take in her own right is never attributed to somebody else, and a mandate also covers a code that needs no authority at all, which is why it is looked up for every procedure a midwife records. The two dropped checks became `policyWarnings` on the row (`DELEGATION_OUTSIDE_ABSENCE_WINDOW`, `OVERLAPS_EXISTING_MANDATE`): recorded and shown, never refused. FR-FORM-03 is modelled as `medications.midwife_authority_kind` with a 422 on the prescription route; **no `AUTHORITY_BOUND` row is seeded** (product owner, 2026-09-20) — which medicines are bound is a clinical list this repo does not hold, and inventing KFA codes for it would be worse than an empty template. The maximum duration of a `MANDATE` is still open: PP 28/2024 bounds only the delegation form, so the product refuses an open-ended mandate but does not cap one.

## D-037: A Consultation Fee Is Priced by the Visit, Not by the Clinic

- **Status:** Accepted (supersedes the P9-T03 rule "one active CONSULTATION tariff auto-selected; several → the caller names one")
- **Decision:** A `CONSULTATION` tariff names the audience it prices: `specialty_id` (the poli), `profession` (`DOCTOR` / `MIDWIFE`), both, or neither. Invoice generation reads the clinician who actually held the encounter and resolves the fee from most specific to least — poli **and** profession, then poli, then profession, then the untagged clinic-wide row — and reports a gap when nothing matches. The pure ranking lives in `resolveConsultationTariff` (`@hms/shared-types`) so it is testable away from Prisma. `consultationTariffId` survives on `POST /invoices` as an override for a consultation the price list does not describe; it is never required. Both columns are refused on any other category, by a Zod refinement, a service check against the stored row, and a CHECK constraint.
- **Why:** The old rule had two failure modes and a clinic hit both in order. With the seeded single tariff every visit was billed "Konsultasi Dokter Umum" whatever the patient actually attended — a bidan's patient and a specialist's patient paid the same, silently, because nothing on a tariff could say otherwise. The moment the clinic priced them apart, generation answered `400 Multiple active consultation tariffs exist; specify consultationTariffId` — an instruction the caller could not follow, since no screen in `apps/web` has ever sent that field, and the whole invoice failed rather than the one line. Procedures and vaccinations were already priced from what the visit recorded (ICD-9-CM code, vaccine catalog code); the consultation was the last component still guessed.
- **Consequence:** Nothing in generation throws for a pricing problem any more. An unmatched visit yields `NO_CONSULTATION_TARIFF` naming the poli ("No active consultation tariff prices midwife consultations in Kebidanan"), and two equally specific rows yield a new `AMBIGUOUS_CONSULTATION_TARIFF` rather than a coin flip — the rest of the bill still drafts, and the missing line can be added by hand from the DRAFT. Uniqueness is split: three partial unique indexes keep one live tariff per *tagged* audience (an enum-to-text cast is not `IMMUTABLE`, so one index over a `COALESCE` pair is not available), while the untagged clinic-wide fee is kept unique by the service, which answers 409 naming the row that holds the slot. That split is deliberate — an index covering the untagged rows would refuse to build on exactly the clinics that already carry several of them, the ones this decision exists to unblock. Their rows are untouched by the migration; tagging one with a poli resolves the ambiguity. Existing single-tariff clinics see no behaviour change: the seeded `KONSULTASI-UMUM` is the fallback and still prices every visit.
- **Amendment — a consultation tariff carries no ICD-9-CM code:** found in the pilot on the day D-037 shipped. A clinic priced "Konsultasi Dokter Kandungan" for the Obgyn poli and also mapped it to ICD-9-CM 89.07; the doctor coded 89.07 on the visit, so one row was reached by two collectors — the consultation resolver and the procedure matcher — and the invoice carried the fee twice (350.000 as `CONSULTATION`, 350.000 again as `PROCEDURE`). The cashier had been deleting the second line by hand. The mapping is now refused on `CONSULTATION` rows by a Zod refinement, by the service against the stored row (so moving a mapped procedure tariff into the category fails too), and by `service_tariffs_consultation_no_icd9cm_check`. The migration clears existing `CONSULTATION` codes before adding the CHECK, because it cannot be added over them; the procedure such a code priced is reported afterwards as `NO_TARIFF_FOR_PROCEDURE`, which is correct — the consultation fee already covers it. Generation additionally never bills a tariff id a second time on one invoice, so a row that somehow escapes the boundary still cannot double-charge; that skip reports no gap, because the money was billed.

## D-038: Tax Is Data, Frozen at Issue, and the Product Drafts but Never Files

- **Status:** Accepted (P27-T01, SJ-242; research and scope in `docs/product/prd-clinic-taxes.md`)
- **Number:** D-037 is the previous entry in this file. D-numbers collide with `docs/MVP/decisions.md`, so cite this record as `docs/post-mvp/decisions.md` D-038.
- **Decision:** Clinic taxes are modelled in three layers. (1) A singleton **tax profile** records who the clinic is as a taxpayer — entity type, income-tax regime (PP 55 final or general), PKP status and date, NITKU — next to the NPWP that `ClinicProfile.taxId` already holds, now validated as 16 digits. (2) **Tax codes** with effective-dated rates are attached to tariffs and medications, with a default per category, so a treatment (exempt medical service, 12% × 11/12 goods, programme exemption, not an object) is always resolvable and a new PMK is a new rate row. (3) Each invoice line **snapshots** its code, base, rate and amount when the invoice is issued; nothing later rewrites it. Monthly obligations are produced as **drafts** — computed, finalisable, exportable as CSV, PDF and later Coretax XML — and the clinic pays and files in Coretax itself. A non-PKP clinic never charges PPN, but its lines still record their treatment. Prices are **always** tax-inclusive: the patient sees one price per line and, when the invoice carries PPN, the note "Harga sudah termasuk PPN"; the before/after-PPN breakdown is shown only to administrators, on the tariff and medicine price lists (product owner, 2026-09-19, P27-T04 — there is no "PPN on top" setting). PP 55 eligibility follows PP 20/2026: unlimited for individuals and PT perorangan, four tax years for a koperasi, and for a PT (three years) or CV (four years) only as the transition from a start year no later than 2026; a yayasan is never eligible.
- **Why:** The law moved twice in eighteen months — PMK 131/2024 changed how PPN on goods is computed, and PP 20/2026 took the 0.5% scheme away from CVs and PTs — so rates and eligibility compiled into code would be wrong by the next regulation. Freezing at issue is the same rule D-037 and the lab result snapshots follow: an invoice is a record of what was charged under the rules in force, and a report built from it must reproduce to the rupiah years later. Drafting rather than filing is forced, not chosen: Coretax has no filing API a clinic system can use, the return is the clinic's legal act, and holding DJP credentials would be a liability this product should not carry. Exempt medical services are recorded rather than ignored because a clinic crossing the Rp4.8 billion threshold must register as PKP even when every rupiah it earns is exempt, and must then issue kode-08 faktur for those supplies.
- **Consequence:** Out of this first cut and deliberately so: employee PPh 21 (no payroll exists), PPh 23 / 4(2) on purchases (no vendor-bill model; P27-T11 decides), SPT Tahunan, input-VAT apportionment and e-Meterai. Seven questions — inpatient-medicine PPN, BPJS packages and withholding, bidan eligibility for PP 55, the doctor-fee gross basis, PP 55 cash vs accrual, receipt wording, ambulances — go to a tax consultant (PRD §6); each is behind a documented hook rather than blocking P27-T02..T05. PP 55 omzet is cash-basis until that answer arrives. A stored 15-digit NPWP is flagged, not rejected, so upgrading the identifier never blocks an unrelated edit of the clinic profile.

## D-039: The Operator's NIK Lives on the Account, Encrypted Like a Patient's (P24-T15)

- **Status:** Accepted (P24-T15, SJ-214; enables P24-T16, SJ-215)
- **Number:** D-038 is the previous entry in this file. D-numbers collide with `docs/MVP/decisions.md`, so cite this record as `docs/post-mvp/decisions.md` D-039.
- **Decision:** The NIK of the person at the front desk — the `agent_nik` SATUSEHAT's KYC `generate-url` requires (FR-KYC-02) — is stored on **`User`**, in the four columns every other national identifier in this schema already uses: `nikCiphertext`, `nikIndex` (unique), `nikLast4`, `nikKeyVersion`, written through `NationalIdentifierCryptoService.encryptSearchableIdentifier` and validated by `nikSchema`. A signed-in person may add or replace their own NIK through a self-service route under `me/account`, guarded by the existing `user.update:own`; nobody else's route writes it, and no administrative route reads it back. It is shown as its last four digits, never logged, and never placed in audit metadata — the audit row says `changedFields: ['nik']` and nothing more. One NIK per account: `nikIndex` is unique on `users`. **KYC resolves the operator's NIK in a fixed order**: the clinician profile first (`DoctorProfile.nikCiphertext`, which a doctor or midwife already holds for Practitioner linking), then the account. A midwife who is also the desk therefore needs no second entry.
- **Why:** FR-KYC-03 placed the NIK "on the staff profile from P20-T04", and there is no such table: D-027 (`docs/MVP/decisions.md`) decided a person's name lives on `User` and explicitly declined a `StaffProfile` until richer staff attributes multiply. One identifier does not multiply anything. Putting it on `User` is the same call D-027 made for the name, for the same reason — every "who did this" surface already joins `User`, and a second profile table would exist for one column. The clinician profile is not the answer either: an `ADMIN` has none, and inventing an empty `DoctorProfile` for a receptionist so she can hold a NIK would make her a clinician to every screen that asks. The encryption shape is not a choice at all — `docs/post-mvp/patient-identifiers.md` §1 already says how a NIK is stored in this database, and a second way to store the same identifier would be a second thing to rotate, audit and get wrong. The resolution order (profile first) is what keeps the two places from disagreeing about a clinician: the profile's NIK is the one the clinic verified and links to SATUSEHAT as a Practitioner, so it is the one the platform should see as the agent.
- **Consequence:** One migration adds four nullable columns and a unique index to `users` (stamp `20261213000000`). No backfill: nobody's NIK is known today except clinicians', and theirs stays where it is. **Accepted limitation — blind indexes are unique per table.** `users.nik_index` and `doctor_profiles.nik_index` are two indexes over the same HMAC, so a NIK entered on an account *and* on somebody else's clinician profile is not caught by either constraint; only a NIK duplicated within one table is. A cross-table check would need a query at write time in both directions (and the doctor-management path would have to learn about accounts), and the failure it prevents — one physical person recorded as two people — is the same one the two tables already tolerate for the doctor/account split under D-027. Recorded here so the gap is a decision rather than a surprise; the KYC resolution order means a clinician's account NIK, if ever entered, is simply never used. A later `StaffProfile`, if D-027's condition is met, takes these four columns with it. Changing an account NIK has no SATUSEHAT link to clear (D-035 concerns Practitioner and Patient links; an operator has neither), so the write is a plain replace.

## D-041: PPh 21 on Clinician Fees Is Drafted per Clinician, on the Doctor's Own Tax Identity

- **Status:** Accepted (P27-T07, SJ-248; scope in `docs/product/prd-clinic-taxes.md` §2.4)
- **Number:** D-038 is the previous entry in this file at the time of writing; D-039 and D-040 are reserved for Sprint 35's KYC and maternal-report tickets and land with their own PRs. D-numbers collide with `docs/MVP/decisions.md`, so cite this record as `docs/post-mvp/decisions.md` D-041.
- **Decision:** PPh 21 bukan pegawai on jasa medis is a third monthly report kind, `PPH21_NON_EMPLOYEE`, that follows the P27-T05 draft lifecycle (draft → recompute → finalize, CSV and PDF, never filed — D-038). One BP21 line per clinician per month: gross = the clinician's `grossFee` on the P27-T06 ledger for the month, DPP = 50% of gross, PPh 21 = the Pasal 17(1)(a) brackets applied to that DPP alone (non-cumulative, PMK 168/2023 Pasal 5(1)(e)). The brackets are an **effective-dated table** (`pph21_tax_brackets`, seeded with the UU HPP set from 2022-01-01); the set in force is the latest one starting on or before the first day of the period, so a future set is ignored for an earlier month and a finalized draft names the set it was taxed under. The clinician's tax identity is their **own NPWP**, a new nullable `npwp` on `DoctorProfile` edited on the clinician form, falling back to the **NIK already on the profile** (which Coretax accepts as NPWP). The draft and the PDF carry the identity **masked**; the full NPWP/NIK is a separate read (`GET /tax/reports/:id/identifiers`) and the CSV export, both under `tax-report.read:any` and both audited as `DOCTOR_IDENTIFIER_UNMASKED` on the `tax-report` resource without the value. A clinician with neither NPWP nor NIK keeps their line, flagged "identitas pajak belum lengkap", and the month cannot be finalized (409 `TAX_REPORT_IDENTITY_INCOMPLETE`). The kind is applicable to every clinic regardless of regime or PKP status; the P27-T10 calendar gates the 15th deposit and 20th SPT Masa PPh 21/26 dates on this draft only for months in which the ledger has entries.
- **Why:** Almost every klinik pratama pays clinicians on fee sharing and must withhold monthly, yet none is on payroll, so the employee TER path does not apply and the non-employee rule (50% × Pasal 17) does. Storing the brackets as rows follows D-038: the brackets moved in 2022 (UU HPP added the 35% tier) and will move again; a set in force by date reproduces an old month to the rupiah. The NPWP lives on `DoctorProfile` rather than the fee rule because a clinician has several rules and one tax identity, and the admin form that edits the profile already exists; the NIK fallback avoids re-entering a number the clinic already holds encrypted. Masking the stored draft and auditing the reveal keeps the same UU PDP posture the doctor directory has for the NIK: JSON in `tax_report_drafts` and a stored PDF are copies that would otherwise hold a plaintext citizen identifier. Blocking finalize rather than dropping the line keeps the figure visible — the tax is owed whether or not the identity is on file — while refusing to freeze a BP21 Coretax would reject.
- **Consequence:** `grossFee` (the clinician's share) is the base, per the T06 acceptance; PRD §6.4 (whether the base is the patient-paid amount before the clinic's share) stays open, and `lineAmount` is carried on every line so the answer is a one-line change. Out of scope and unchanged: employee PPh 21 (TER A/B/C, BPMP, BPA1), a per-clinician BP21 PDF (the month's PDF lists all clinicians), the Coretax BP21 XML converter (P27-T09), and PPh 21 on a clinician who is also an employee. A 15-digit NPWP is accepted and stored like the clinic's own (D-038). Re-run `pnpm db:seed` after deploying for the bracket rows; without them a PPh 21 draft refuses to compute (409 `TAX_BRACKETS_UNAVAILABLE`).

## D-042: Visit Reminders Have Their Own Consent, Honoured by the One Opt-Out Handler

- **Status:** Accepted by the user for the consent shape (2026-09-22); pending product/legal review of the remaining points below (P25-T17, SJ-240). Cite as `docs/post-mvp/decisions.md` D-042.
- **Decision:** WhatsApp reminders of due maternal visits run under a **new, separate consent**, `patient_visit_reminder_consents` (one row per patient, `purpose` fixed to `VISIT_REMINDER` by a CHECK), captured at the desk from a toggle on the patient record and recorded against the privacy-notice version in force at capture (read server-side, as delivery consent does), with the capturing user, time, and revocation reason (`STAFF` or `PATIENT_KEYWORD`). `PatientDeliveryConsent` is neither reused nor given a purpose column. STOP / BERHENTI revokes it through the **existing** `InboundOptOutHandler` (`DeliveryOptOutService`), which now revokes both consents for every patient the chat is proven for and confirms once, in copy that names both. The reminder worker (`MATERNAL_REMINDERS_ENABLED`, off by default) sends only to a patient with granted `VISIT_REMINDER` consent **and** a WhatsApp link verified for her through the delivery pipeline's `DeliveryChannelGateService`, never to the typed number; it sends from 09:00 to noon clinic-local, at most once per `(patient, visit key)` by a unique index on `maternal_visit_reminders`, one message per patient per sweep covering all her newly due visits, with one attempt per visit (a failed send is recorded `FAILED`, not retried). The due list is gathered from the P25-T06/T10/T12/T14 services (`MaternalVisitDueService`); the reminder module owns no due rule.
- **Why:** The patient consented to document delivery for that purpose; reminding her of visits is a different purpose, and UU PDP's (UU 27/2022) purpose-limitation principle means it needs its own lawful basis — a separate row with its own notice version and its own withdrawal is the simplest form that can be shown to an auditor. Requiring a verified link rather than the typed phone number keeps a reminder that implies pregnancy or a birth off a mistyped or shared number (the verified-number reasoning of FR-E4-03), and it is what makes STOP work: the opt-out finds patients by the chat they were proven on, so a reminder sent to an unverified number could not be stopped by replying to it. Reusing the one handler keeps "STOP means stop" true for every outbound purpose.
- **Consequence:** A patient who consents but has no verified WhatsApp link is on the worklist and receives nothing until her number is verified (the delivery OTP flow). Visit labels in the message are deliberately coarse ("kunjungan kehamilan / nifas / bayi / kontrol"; KB and SHK are never named). No message body or phone number is stored on the reminder row. Open for product/legal: (1) whether the general privacy-notice version is a sufficient "notice version" for this purpose or a reminder-specific notice text is needed; (2) whether the verified-link requirement is acceptable for the pilot or a typed number should suffice; (3) the send window and one-attempt policy; (4) whether a STOP answering a reminder should also revoke delivery consent (today it revokes both). Out of scope: SMS and email, reminders without consent, any change to document-delivery consent.
## D-043: The Non-Capitation Recap Is Derived From Care Records, With the Induk as Its Own Settings Row

- **Status:** Accepted (P25-T16, SJ-239; re-scoped by the P25-T13 spike `docs/ops/bpjs-bidan-jejaring-claims-spike.md`; user decision 2026-09-22 that everything Q12 decides is admin-configurable)
- **Number:** D-041 is the previous entry in this file; D-042 and D-044 are reserved for Sprint 36's reminder and tax tickets and land with their own PRs. Cite this record as `docs/post-mvp/decisions.md` D-043.
- **Decision:** The bidan jejaring's monthly BPJS non-capitation recap is a file for the induk FKTP, never a PCare submission. Its lines are **derived on read** and only the "sent to the induk" mark is stored (`bpjs_non_capitation_claim_marks`, unique per service type and source). A BPJS participant is a patient with a BPJS number; no PCare config is required, because a jejaring PMB holds none (spike §0–§1). The induk is a **singleton settings row** (`bpjs_non_capitation_settings`: induk code and name, government-owned yes/no/unknown, own eClaim login yes/no/unknown, filing day 1–28 defaulting to the 10th), not columns on `bpjs_pcare_configs` as the original ticket said. Tariffs are rows by validity window, seeded from Permenkes 3/2023 Pasal 19–22 (pp. 13–16) as the spike quotes them; a new row closes the open one the day before and may not start on or before an existing row. The payable units and the rules that derive them: ANC per FINISHED antenatal encounter, at the bidan rate when the encounter's clinician is a midwife, the doctor rate otherwise, and the doctor-with-ultrasound rate when an ICD-9-CM 88.78 procedure is on the encounter; a pra rujukan line for an antenatal or nifas encounter that has a surat rujukan filed on it or a live PCare referral; delivery priced by **the attendant's profession standing for the team** (doctor → Pasal 20 ayat (2) huruf a–b, Rp1.200.000; midwife → the two-nakes-no-doctor line, Rp800.000); PNC per FINISHED KF visit of the mother (KF1–KF3 as mother and newborn, KF4 as mother); KB for an AKDR or implant course **started here by a NEW acceptor**, and every injection (an injectable course start, and each follow-up that set the next due date). A supporting document counts for a line when it is filed on one of the line's patients (the mother, and for a birth her registered babies) and either sits on the line's encounter or stay, or sits on no visit and is dated on or after the service; three categories are added for what Peraturan BPJS 7/2018 Pasal 13–14 asks for and no category named (`KIA_BOOK_COPY`, `PARTOGRAPH`, `FAMILY_PLANNING_BOOK`). The mark request carries the month, and a source that is not a line of that month's recap is answered `NOT_IN_RECAP`.
- **Why:** The spike found no PCare write endpoint and no jejaring credentials, and the claim is legally the induk's document set, so a derived recap plus a mark is the whole job; storing lines would be a second copy of the care record that drifts from it. Keying off the BPJS number rather than the outbox is the spike's explicit instruction. A separate settings row lets a PMB with no PCare config name its induk and keeps Q12's answers out of the credential table. No delivery-team record exists; the attendant is the one fact the birth record holds about who was there, and it errs toward the lower tariff for a midwife, which the induk can correct against the partograf. A document dated before the service cannot be a copy of that service's KIA page.
- **Consequence:** Under D-033's billing-line opening a line carries only participant (name and BPJS last four), service type, date, visit code, examiner profession, tariff with its reference, document-category presence and claim status; no diagnosis, finding or document content is read or returned. Keys `bpjs.non-capitation.read:any` and `.write:any` are ADMIN's and not clinical content. The 10% biaya pembinaan is shown only as a ceiling and only for an induk known not to be government-owned. Out of scope and open: a recorded delivery team (would correct the tariff inference), IUD and implant removals, KB complication and MOP lines (seeded tariffs are not; the model does not record them), a full BPJS number in the export (it stays masked; the induk looks it up in eClaim or the admin reveals it through `patient.read-identifier`), and a backlog view of unsent lines from earlier months still inside their six months. Re-run `pnpm db:seed` after deploying for the tariffs and the two keys.
## D-044: Coretax XML Follows DJP's Published Converter, Byte for Byte, From Verified Artefacts Only

- **Status:** Accepted (P27-T08, SJ-249). Sprint 36; D-042 and D-043 are reserved for the same sprint's other tickets. D-numbers collide with `docs/MVP/decisions.md`, so cite this record as `docs/post-mvp/decisions.md` D-044.
- **Decision:** A Coretax export produces the XML DJP's own Excel→XML converter would produce from the same rows, and nothing is modelled from memory. For BP21 the source is the **v4 workbook** ("BP21 Excel to XML v.4", catalogue date 17/04/2025, pajak.go.id node 112031; SHA-256 recorded in `CORETAX_BP21_TEMPLATES`): its embedded XML map is the schema (checked in, verbatim, as `apps/api/test/fixtures/coretax/bp21-v4.xsd`), its REF sheet gives the codes, and the `bp21.xml` sample DJP publishes beside it gives the serialization (UTF-8 declaration with `standalone="yes"`, CRLF, tab indentation, no final newline). Each template version is a constant plus one serializer in `CORETAX_BP21_XML_SERIALIZERS`; a new DJP version adds both and keeps the old ones, so a finalized month re-exports identically. Only a **FINALIZED** `PPH21_NON_EMPLOYEE` report exports (`GET /tax/reports/:id/coretax/bp21`); `…/bp21/validation` lists every problem at once, per clinician, and reads no identifier back. The mapping: withholder `TIN` = clinic NPWP (16 digits; a 15-digit legacy NPWP is refused), `IDPlaceOfBusinessActivity` = clinic NITKU; per clinician `CounterpartTin` = own NPWP else NIK (16 digits), recipient NITKU = that number + `000000` as in DJP's sample, `StatusTaxExemption` = a new nullable `DoctorProfile.ptkpStatus`, `TaxCertificate` = `N/A`, `TaxObjectCode` = `21-100-07` (tenaga ahli, dokter) for a doctor and `21-100-20` (pemberi jasa) for a midwife, `Gross` = the draft's gross fee, `Deemed` = 50, `Rate` = the Pasal 17 bracket the DPP lands in (the converter's `PS17` column), `Document` = `PaymentProof` with number `JM/<YYYY-MM>/<first 8 of the clinician id>`, and both dates = the last day of the month. A clinician whose month nets to exactly zero is left out (no bukti potong is due); a negative month blocks. The download is audited as `EXPORT` and `DOCTOR_IDENTIFIER_UNMASKED`, without values.
- **Why:** A file Coretax rejects is worse than none: the clinic learns at upload, after the deadline pressure has started. The golden file is only as good as its source, so the source is DJP's own published artefacts, pinned by hash, and the test validates the output against DJP's schema with `xmllint` where available. PTKP is on the profile because the schema requires it on every line although the bukan pegawai tax never reads it; inventing `TK/0` for everyone would put false data on a tax document.
- **Consequence:** Open, and listed for the product owner: (1) the midwife's object code `21-100-20` and the doctor's `21-100-07` want the tax consultant's confirmation (PRD §6); (2) `Rate` is the single marginal bracket the converter picks, while the draft taxes progressively — identical below Rp60 juta DPP, and above it Coretax's own computation is authoritative, so the first real upload (a pilot clinic, product owner's closing step) must compare Coretax's PPh with the draft; (3) the schema's `DocType` enumeration is older than the v4 REF sheet (`Other`, `Decree`, … exist only in the sheet) — the export uses `PaymentProof`, which is in both; (4) the withholding date is the month's last day, not the payout date, because the ledger has no payout date. One migration adds `doctor_profiles.ptkp_status` (enum `ptkp_status`, stamp `20261226000000`); no seed change, no new permission (the routes use `tax-report.read:any`).

## D-045: A Practice Session Moves Within Its Own Week, by the Admin, and Owes Nothing When It Does Not

- **Status:** Accepted 2026-09-23 (P28, SJ-261..265) — the product owner's answers to the "Reschedule Appointment — Strategy" page. Cite as `docs/post-mvp/decisions.md` D-045.
- **Decision:** A doctor who cannot hold one occurrence of their weekly practice window arranges it with the clinic administration privately, and the **admin** performs the change — `appointment.session.update:any` only, no doctor-side control. The occurrence either **moves** to another window in the **same Monday–Sunday week** (clinic timezone), at any time including after it has started (the doctor-arrives-late case), or is **cancelled** with a reason. There is no third state: a session that is not moved carries **no replacement obligation**, because jasa medis is paid per consultation (P27-T06), so nothing is owed. The move leaves the original as a `MOVED` tombstone at its original start (linked to the replacement) and never edits the weekly `DoctorSchedule`. Within the same day every open booking follows, checked-in and BPJS bookings included; to another day, bookings with a live registration and BPJS bookings stay behind and are returned as a front-desk worklist, never silently cancelled. Moved bookings keep their id, booking code and queue number. Every move and cancellation records its reason in `appointment_session_changes` and notifies each patient with an account. Patients do not reschedule session bookings themselves.
- **Why:** The weekly schedule is a promise for every future week, so a one-week problem must not edit it; a tombstone at the original start is what stops the projection from quietly re-offering the slot. Keeping the change inside the week keeps the patients' plans and the clinic's per-week reporting intact, and keeping it with the admin keeps one person accountable for telling the patients.
- **Consequence:** A session row describes its own start time only in the check-in window rule (P19-T16), so a replacement landing on a day with its own weekly window no longer hides that window. `PATCH /appointment-sessions/:id` no longer cancels — cancelling needs a reason.


## D-046: The Attending Clinician Prescribes for the Visit They Are Holding, Without a Separate Assignment

- **Status:** Accepted 2026-09-25 (product owner). Narrows D-017 in `docs/MVP/decisions.md` for prescribing only. Cite as `docs/post-mvp/decisions.md` D-046.
- **Decision:** Under `prescription.write:own`, a clinician — doctor or midwife (D-034) — may prescribe for a patient without an active `DoctorPatient` assignment when the prescription names an encounter that is `IN_PROGRESS`, belongs to that same patient, and whose attending clinician is the caller. A prescription that names no encounter, or names one the caller is not attending, or one already finished, keeps D-017's rule: an active assignment is required. `prescription.write:any` is unchanged. The midwife formulary (P24-T04) and midwife authority checks (P25-T05) apply to the attending midwife exactly as before; the visit authorises the patient, not the medicine.
- **Why:** Opening an encounter never needed an assignment — the checked-in registration is the authorisation, because walk-ins are the normal case in an FKTP — so a walk-in registered without a doctor could have diagnoses, procedures and lab orders written by the clinician examining them, and then no prescription: `POST /prescriptions` answered 403 "You can only prescribe for patients actively assigned to you". The two rules contradicted each other on the one step a visit most often ends with. D-033 already says the clinical record is for the clinicians who examine the patient; the attending clinician of the open visit is that person.
- **Consequence:** No assignment is created or inferred (D-017's "never implicit" stands); the reach is the open visit and ends when it closes. Reading and printing what the clinician wrote needs no change: prescription `:own` reach is participant-side (`build-prescription-scope-where.ts`, and the resep PDF's participant check), and the attending clinician is the prescribing doctor on the row. A clinician who is neither attending nor assigned — a colleague looking at the same walk-in — is still refused.

## D-047: The Clinic Manages Its Own Poli, and Kebidanan Is the Midwife's Poli

- **Status:** Accepted 2026-09-25 (product owner). Cite as `docs/post-mvp/decisions.md` D-047.
- **Decision:** The specialty catalog, which the clinic calls its poli, can now be managed. An administrator holding `specialty.manage:any` (seeded to `ADMIN`; `SUPER_ADMIN` holds it through the catalog-wide grant) can add a poli, rename it, change its description, deactivate it and reactivate it, from `/admin/settings/poli`. A poli is never deleted. Deactivation is refused with `409 SPECIALTY_IN_USE`, and the counts in `details`, while an active clinician practises under the poli or an active tariff prices it. Names are unique without regard to case (`409 SPECIALTY_NAME_TAKEN`). The seed adds `Kebidanan`. A new midwife profile defaults to it when the clinic runs one, and the demo midwife now uses it instead of `Obstetrics & Gynecology`.
- **Why:** Specialties were a fixed English seed list with a read-only API, so a clinic could not open a Kebidanan poli. Midwives had to be filed under Obstetrics & Gynecology, which is a physician specialty. The poli is what a visit queues for, what a consultation tariff is priced by (D-037), which SATUSEHAT Location a visit reports under, and which BPJS kdPoli it registers with. It is clinic set-up, and the clinic should own it.
- **Consequence:** Renaming is safe. Mappings hang off the row's id and its own `bpjs_poli_code` / `satusehat_location_id` columns, never its name. A rename does not rename a SATUSEHAT Location that is already registered, and invoices and reports show the new name. The seed becomes insert-only for specialties, so a re-seed keeps an admin's deactivation and skips a seeded row the clinic has renamed. Without that, the renamed row's derived id would collide and fail the whole seed. The English names stay as seeded. A clinic that wants Indonesian names renames them in the app, and no separate display-label column was added.

## D-048: Clinic Hand-Off Notifications Go to the Next Person in the Visit, Never the Actor

- **Status:** Accepted 2026-09-25 (product owner request for the clinic demo). D-046 and D-047 are reserved for parallel Sprint work. Cite as `docs/post-mvp/decisions.md` D-048.
- **Decision:** Five bell rows announce a hand-off between roles, each written best-effort after the business act commits (a failed bell never fails the act) and never addressed to the person whose action raised it. `LAB_ORDER_CREATED` goes to every holder of `lab-specimen.write:any` (the bench: LAB_TECHNICIAN and ADMIN), for encounter and walk-in orders alike, and only for orders the clinic's own lab runs (`fulfilmentSite = INTERNAL`); an order sent out never reaches the worklist. `PATIENT_CHECKED_IN` goes to the account behind the clinician the checked-in visit's appointment is booked with; a walk-in with no appointment names no clinician and tells nobody. `PATIENT_ASSIGNED` goes to each clinician with an account newly put on a patient's care team, from `POST /doctor-patient-assignments`, from a booking that assigns, and from a patient registered with `doctorIds`; an idempotent re-assign tells nobody. `CLINICIAN_JOINED` goes to holders of `doctor.update:any` when an invitation bound to a clinician profile is accepted; `STAFF_JOINED` goes to holders of `user.create:any` when any other invitation is accepted. Links are written per recipient shell through `NotificationHrefService`: the lab order opens the encounter for a doctor-shell reader and the admin order page for everyone else; a check-in opens the doctor's day agenda (`/doctor/appointments?view=day&date=…`), the doctor shell having no queue page, or the admin queue; an assignment opens the patient page in the reader's shell; the joined rows link only for admin-shell readers. The bell rows carry names and counts, never clinical content.
- **Why:** A demo clinic shows a visit passing from desk to clinician to lab, and each person should learn that work has arrived without refreshing a list. Addressing by permission rather than role name keeps custom roles working. LAB_TECHNICIAN was the one seeded staff role without the staff baseline keys (`notification.*:own`, `feature.read-availability:own`), so the bench had no bell to receive its own notification; the seed now grants them and `staff-role-baseline-seed.spec.ts` fails CI when any seeded staff role lacks a baseline key.
- **Consequence:** One migration adds the five enum values (stamp `20270104000000`). Re-run `pnpm db:seed` for the LAB_TECHNICIAN grants. Out of scope: e-mail or WhatsApp delivery of these events, a doctor-shell queue page, and notifying on unassignment.
