# HMS Implementation Plan (Post-MVP)

Continuation of [docs/MVP/implementation-plan.md](../MVP/implementation-plan.md). MVP phases end at Phase 5 (hardening); this plan starts at Phase 7. Same delivery principles apply: one branch per task (`feature/p<phase>-t<task>-<short-desc>`), strict `repository -> service -> controller` layering, mandatory quality gates before merge.

## 1. Why This Order (Market and Regulatory Context)

Research summary (July 2026), full context in session research:

- PMK No. 24/2022 legally mandates electronic medical records (RME) and SATUSEHAT integration for **all** facilities including clinics and solo practices; the compliance deadline (Pasal 45) was 31 December 2023, so the mandate is already past due for every prospective customer.
- Incumbent vendors bundle compliance at their cheapest tiers: Trustmedis includes RME + SATUSEHAT + BPJS PCare at Rp99k/month; Klinik Pintar bundles billing, inventory, queue management, and BPJS at Rp300k/month and offers a free solo-doctor tier.
- The market is fragmented (a major EMR vendor reached only ~8.9% of eligible FKTPs after 33 months) and purchases are driven by regulatory deadlines, not organic demand.

Conclusion: compliance features (coded EMR, SATUSEHAT, BPJS) and front-desk basics (queue, billing) are the purchase triggers for Indonesian small clinics. They are ordered first below. The AGENTS.md MVP scope note ("do not expand scope until MVP modules are stable") is superseded by this plan once Phase 5 (MVP hardening) is complete.

## 2. Phase 7 - Clinical Data Model Enrichment (Backend, 7 Tasks)

Goal: extend `PatientProfile`, `DoctorProfile`, and `Medication` with the identity and credential fields required by PMK 24/2022, SATUSEHAT, and BPJS — **before** more production data accumulates. All fields go through `packages/shared-types` schemas per repo convention.

Identifier storage and MRN allocation are specified in [patient-identifiers.md](./patient-identifiers.md) — read it before starting `P7-T01`.

### 2.1 Patient fields (`P7-T01`, `P7-T02`)

1. `P7-T01` Migration + schema: national identity and payer fields. Land these columns **already encrypted** (`P7-T07`) so no plaintext window exists.
   - `nik` (16 digits, nullable — newborns/foreigners may lack one). Stored as `nikCiphertext` + `nikIndex` (unique) + `nikLast4`; validate structure, not a checksum — NIK has none, but digits 7–12 encode `DDMMYY` with +40 on `DD` for female, so it cross-checks against `dateOfBirth`/`gender` as a soft warning. SATUSEHAT uses NIK as the master patient index key (`https://fhir.kemkes.go.id/id/nik` identifier system).
   - `bpjsNumber` (13 digits, nullable). Same encrypted + blind-index treatment, unique on the index.
   - `satusehatPatientId` (IHS number, nullable — filled after first successful SATUSEHAT patient lookup/registration). Encrypted, no blind index.
   - `placeOfBirth`. **Do not add `gender`** — `PatientProfile` already has `sex PatientSex?` with the same `MALE | FEMALE` values; keep one field and map it to FHIR `gender` in the SATUSEHAT adapter.
2. `P7-T02` Migration + schema: demographic and clinical-safety fields required by PMK 24/2022 patient identity / expected by clinics.
   - `bloodType` (enum A/B/AB/O + rhesus), `maritalStatus`, `occupation`, `religion` (optional; present on Indonesian registration forms and PCare).
   - `email` (optional), `emergencyContactName`, `emergencyContactPhone`, `guardianName`/`guardianRelation` (penanggung jawab — required for minors).
   - `allergies` as a structured list (free-text substance + reaction severity enum for now; coded later in EMR phase).

### 2.2 Doctor fields (`P7-T03`, `P7-T04`)

3. `P7-T03` Migration + schema: licensing and identity.
   - `nik` (unique, required for SATUSEHAT practitioner lookup). **Encrypted at rest exactly like a patient NIK** — a practitioner NIK is the same citizen identifier and carries the same UU PDP obligations, so it uses the `nikCiphertext` / `nikIndex` / `nikLast4` / `nikKeyVersion` scheme from [patient-identifiers.md](./patient-identifiers.md) §3 and is masked in every response. Only STR/SIP numbers are registry-public and stay plaintext, on `DoctorLicense`.
   - `strNumber` (Surat Tanda Registrasi — SATUSEHAT resolves practitioners against STR data). Note: under UU Kesehatan No. 17/2023 STR is now lifetime, so no expiry field; verify current rule at implementation time.
   - `sipNumber` + `sipExpiresAt` (Surat Izin Praktik — per practice location, time-limited; clinics must track expiry for licensing audits). Model as a `DoctorLicense` child table (type enum `STR | SIP`, number, issuedAt, expiresAt nullable) rather than flat columns, so multi-SIP doctors are representable.
   - `satusehatPractitionerId` (IHS number, nullable).
4. `P7-T04` Migration + schema: profile fields clinics expect on doctor listings.
   - `specialty` (enum or reference table: umum, gigi, spesialis codes), `title`/`degrees` (e.g. `dr., Sp.PD`).
   - `DoctorEducation` child table: institution, degree, fieldOfStudy, graduationYear (SATUSEHAT `Practitioner.qualification` maps from this + licenses).
   - `phoneNumber`, `email` on DoctorProfile (SATUSEHAT Practitioner requires at least one ContactPoint).

### 2.3 Medication fields (`P7-T05`)

5. `P7-T05` Migration + schema: `kfaCode` (Kamus Farmasi dan Alat Kesehatan code, nullable, unique when present — required for SATUSEHAT medication resources), `unit` (tablet/kapsul/ml), `category`. Add the missing medication create/update admin endpoints (catalog is currently read-only via API).

### 2.4 Identifier handling (`P7-T06`, `P7-T07`)

Design: [patient-identifiers.md](./patient-identifiers.md).

6. `P7-T06` MRN auto-generation. **Done.** `MrnCounter` migration + atomic `UPDATE … RETURNING` allocation inside the patient-create transaction (`MrnAllocatorRepository` in `apps/api/src/common/mrn/`); `mrn` removed from `createPatientSchema` and response-only from here on; admin legacy-import path (`POST /api/v1/patients/import`) gated by `patient.import-identifier`, which lifts the counter past every imported number; uniqueness scope decided as **single-facility** (global `@unique`, one counter row on the nil-UUID sentinel). MRN is immutable — no update path. Format via `PATIENT_MRN_PREFIX` / `PATIENT_MRN_WIDTH`. Concurrency proven against real Postgres in `mrn-allocation.integration.spec.ts`, which is why CI now runs `integration:test` after `migrate deploy`.
7. `P7-T07` Identifier encryption at rest. **Done.** `NationalIdentifierCryptoService` in `apps/api/src/common/crypto/` (AES-256-GCM for ciphertext, HMAC-SHA256 blind index for lookup/uniqueness — a plain hash is brute-forceable because name/DOB/address sit in plaintext in the same row); shared normaliser used by every write path; masked-by-default responses with dedicated unmask routes behind `patient.read-identifier` and `doctor.read-identifier`, each emitting an audit event naming the revealed fields but never their values; `PATIENT_PII_ENCRYPTION_KEY` + `PATIENT_PII_INDEX_KEY` (both distinct from `AI_PROVIDER_ENCRYPTION_KEY`); key- and pepper-rotation procedures in [deployment-runbook.md](../ops/deployment-runbook.md) §5.1–5.2.

Phase 7 notes:

- Every new field is optional/nullable at the API layer except where noted, so existing MVP data and flows keep working; enforce required-ness progressively in the EMR/SATUSEHAT phases.
- Update seeders, integration tests, and regenerate the web client (`pnpm api:contract:sync`) per task.
- `P7-T06` and `P7-T07` must land with (or before) `P7-T01` — retrofitting either onto live clinical records means a plaintext window plus renumbering MRNs already printed on physical folders.
- Never put real NIK or BPJS values in seeders or fixtures; use structurally valid synthetic values.

## 3. Phase 8 - Encounter / EMR Module and Queue (Backend, 6 Tasks)

Goal: the legally mandated clinical record. New module `emr` (or `encounter`) following standard layout. PMK 24/2022 minimum outpatient record content: verified patient identity, date/time, anamnesis (complaint + history), physical and supporting examination results, diagnosis, treatment plan, medication/actions given.

1. `P8-T01` Schema: `Encounter` (links registration, patient, doctor; status enum `IN_PROGRESS | FINISHED | CANCELLED`; startedAt/endedAt). One encounter per completed registration. **Done.** `encounters` table with `registrationId` `@unique` (a same-day second visit is a second registration); `doctorId` denormalised onto the encounter rather than read through the appointment, because walk-ins have no appointment and the attending doctor may differ from the booked one — the record must name whoever signed it. Both closed states are terminal (`ENCOUNTER_STATUS_TRANSITIONS` in `@hms/shared-types` `#emr/schemas`): corrections supersede, never re-open. All FKs `RESTRICT` so a clinical record can't be orphaned. No API surface yet — the module lands in `P8-T05`.
2. `P8-T02` Schema: `VitalSigns` on encounter — height (cm), weight (kg), systolicBp, diastolicBp, pulseRate, respiratoryRate, temperature, spO2. Store LOINC mapping in the SATUSEHAT adapter, not the DB. **Done.** Modelled **many rows per encounter**, not one: re-measuring after an abnormal reading is routine and an overwrite would erase the finding that prompted the recheck, so each row is an independent measurement stamped with `recordedAt` / `recordedById` — which is also how it maps 1:1 to a SATUSEHAT `Observation` in `P10-T03`. "The" vitals for a submission or summary are the newest row (`@@index([encounterId, recordedAt])`). Columns use complete words (`systolicBloodPressure`, `oxygenSaturation`) per the repo naming rule; units are fixed by the column so there is no unit column, and no LOINC code reaches the DB. BMI is derived on read, never stored — a stored copy goes stale when either input is corrected. Hand-written CHECK constraints in the migration reject physiologically impossible values (a decimal typo turning 36.8 °C into 368, or a transposed 80/120) but never merely abnormal ones; Prisma cannot express CHECKs, and `migrate diff` ignores them, so CI's drift gate stays green (verified). Bounds are exported once as `VITAL_SIGNS_BOUNDS` in `#emr/schemas` so `P8-T05`'s Zod schema derives from the same numbers.
3. `P8-T03` Schema: `Diagnosis` — `icd10Code` + display text, type enum `PRIMARY | SECONDARY`, per encounter. Ship an `Icd10Code` reference table + seed (WHO/Kemenkes list) with a search endpoint. **Done.** `Diagnosis` stores `code` + `display` as a **snapshot of what was signed**, with `icd10CodeId` only as nullable provenance (`SetNull`): renaming or retiring a catalog row must never rewrite a signed record. Two hand-written partial unique indexes enforce one `PRIMARY` per encounter and no duplicate code per encounter, both scoped to `deleted_at IS NULL` so a soft-deleted row cannot block a correction — Prisma cannot express `WHERE` on an index, and `migrate diff` ignores them, so CI's drift gate stays green (verified). Catalog rows are deactivated, never deleted, so historic diagnoses keep resolving. Search endpoint `GET /api/v1/icd10-codes` lives in a new **`terminology` module** (reference data is not encounter logic; `P8-T04`'s ICD-9-CM procedures belong here too), gated by a new `icd10-code.read:any` permission granted to ADMIN and DOCTOR. It matches code prefix plus **both** the English and Indonesian titles, since clinicians search in either. **The seed is a ~58-code starter set of common FKTP diagnoses, not the official list** — the official Kemenkes catalog is loaded with `pnpm --filter @hms/api icd10:import <file.csv>`, which upserts by code and deactivates absent codes in one transaction. Replace the starter set before go-live.
4. `P8-T04` SOAP note fields on encounter: `subjective` (anamnesis), `objective` (exam findings), `assessment`, `plan`; procedures as ICD-9-CM coded rows (`Procedure` table) — needed later for BPJS claims. **Done.** SOAP columns are free text on the encounter, deliberately uncoded: the coded conclusions live in `diagnoses` (ICD-10) and `procedures` (ICD-9-CM), and forcing narrative reasoning into codes loses detail a later reader needs. `Procedure` mirrors `Diagnosis` — signed `code`/`display` snapshot, `icd9cmCodeId` as nullable provenance, and a partial unique index on `(encounterId, code) WHERE deleted_at IS NULL` — but has no primary/secondary split, since every procedure counts equally toward a claim; repeat quantity belongs on the claim line, not in duplicate rows. `Icd9cmCode` joins `Icd10Code` in the `terminology` module with `GET /api/v1/icd9cm-codes` and a new `icd9cm-code.read:any` permission (ADMIN + DOCTOR). It carries **no chapter column** — ICD-9-CM procedure chapters do not follow a clean lexicographic range the way ICD-10 chapters do, so only the two-digit `category` is derived. The `P8-T03` importer was generalised into `import-terminology-codes.ts <catalog> <file>` rather than duplicated; `icd10:import` is unchanged and `icd9cm:import` is new. **The ICD-9-CM seed is a deliberately small 17-code starter set** — BPJS prices claims from these codes, so an approximate catalog is a billing problem, not a display one. Replace it via `icd9cm:import` before go-live.
5. `P8-T05` Encounter service/controller: open encounter from a `CHECKED_IN` registration, record vitals/SOAP/diagnoses, close encounter (transition registration to `COMPLETED`); link prescriptions to the encounter. **Done.** New `emr` module with two controllers — `/encounters` for the lifecycle and `/encounters/:encounterId/...` for the measured and coded content, which is appended and retracted independently of the record it hangs off. Closing writes the encounter and its registration **in one transaction**: they describe the same visit from the clinical and the front-desk side, and committing one without the other leaves a finished patient still queued. Cancelling retracts the registration with it — `registrationId` is `@unique`, so a mistakenly opened record cannot be replaced in place and the patient re-registers. Diagnoses and procedures are retracted by soft delete, which is exactly what the `deleted_at IS NULL` partial unique indexes from `P8-T03`/`P8-T04` were built for: the row stays auditable while the code and the `PRIMARY` slot free up for the correction. **Coding snapshots the catalog, not the request** — naming an `icd10CodeId` makes the server copy that row's code and title, so a client can never sign a display that disagrees with the code it claims; a code the catalog does not carry yet is supplied as an explicit `code` + `display` pair. Vitals are append-only (a recheck must not erase the reading that prompted it), their request schema derives its ranges from `VITAL_SIGNS_BOUNDS` so Zod and the CHECK constraints cannot drift, and BMI is computed on every read rather than stored. Four new permissions (`encounter.read`/`write` × `any`/`own`): **write is narrower than read** — under `OWN` only the attending practitioner signs the record, while reading also covers the patient and any doctor currently assigned to them, because reading the previous visit is part of conducting the next one. `Prescription.encounterId` is nullable (repeat prescriptions are issued between visits, and MVP rows predate encounters) and only accepts an `IN_PROGRESS` encounter for the same patient.
6. `P8-T06` Queue numbers: per-day, per-poli sequential queue number generated on registration (`queueNumber`, `queueDate` indexed); endpoints for today's queue board. Small task, high demo value — Indonesian clinics operate on antrian. **Done.** `queueNumber`/`queueDate` land on `Registration`, allocated inside the registration-create transaction from a per-day `QueueCounter` row with one atomic `INSERT … ON CONFLICT … RETURNING` — the `MrnCounter` reasoning applied per day (a `MAX + 1` race hands two patients the same ticket), proven against real Postgres in `queue-number-allocation.integration.spec.ts`. A rolled-back create returns its number to the pool; a committed one is never reissued — a cancellation leaves a gap, exactly like a paper ticket roll. The queue is **clinic-wide, not per-poli**: the deployment has no poli concept yet (single facility, same call as the MRN scope decision), so the per-poli split arrives with the BPJS poli mapping (`P11-T03`). `queueDate` is the clinic-local (`CLINIC_TIMEZONE`) calendar day, stamped explicitly at allocation so the board query never re-derives day boundaries from UTC timestamps — a 23:30 UTC registration already belongs to tomorrow's antrian in Asia/Jakarta. Board endpoint `GET /api/v1/registrations/queue-board` (defaults to today, entries in ticket order plus per-status counts) demands `registration.read:any` — it lists every patient by name, so the OWN-scoped patient role is refused and reads its own number off its registration instead. Distinct from the pre-existing per-session `Appointment.queueNumber` assigned at check-in: that orders patients inside one doctor's session; this is the clinic's daily front-door queue.

## 4. Phase 9 - Billing / Kasir Module (Backend, 4 Tasks)

Goal: minimum viable cashier — every incumbent bundles this at the pratama tier.

1. `P9-T01` Schema: `ServiceTariff` (consultation/action price list), `Invoice` + `InvoiceItem` (auto-collect from encounter: consultation fee, procedures, dispensed medications), status enum `DRAFT | ISSUED | PAID | VOID`. **Done.** All money is `Decimal(12, 2)` rupiah with CHECK constraints rejecting negatives — never floats, never `Int` (a clinic invoice can plausibly exceed the 2.1B int ceiling). `Invoice.encounterId` is deliberately **not** `@unique`: a wrongly issued invoice is corrected by VOID (reason + audit in `P9-T03`) plus a replacement for the same encounter, so a hand-written partial unique index (`WHERE status <> 'VOID' AND deleted_at IS NULL`) enforces at most one live invoice per encounter — the diagnosis partial-index trick applied to billing; Prisma can't express it and `migrate diff` ignores it, so CI's drift gate stays green (verified). `InvoiceItem` applies the `Diagnosis` snapshot rule to money: `description`/`unitPrice`/`amount` are what was billed, `serviceTariffId`/`medicationId` are `SetNull` provenance, and a CHECK pins `amount = quantity * unit_price`. `Invoice.totalAmount` is stored (unlike BMI): the total of a financial document is part of what was issued, recomputed from items only while DRAFT. `ServiceTariff` is reference data like the terminology catalogs (deactivate, never delete) with a unique optional `icd9cmCode` so procedure auto-collect resolves at most one tariff per code. `Medication.unitPrice` (nullable) added because dispensed-medication billing needs a price source the catalog lacked — an unpriced dispensed item is a gap to surface, not a free line. `InvoiceCounter` (per-day, mirroring `QueueCounter`) lands now so `P9-T03` allocates invoice numbers with one atomic upsert instead of a racing `MAX + 1`; a committed number is never reissued, so a voided invoice leaves a gap exactly like a torn receipt. Status transitions live in `#billing/schemas` (`INVOICE_STATUS_TRANSITIONS`): DRAFT→ISSUED|VOID, ISSUED→PAID|VOID; PAID is terminal for v1 (refunds out of scope) and VOID terminal by definition. No API surface yet — the module lands in `P9-T03`.
2. `P9-T02` Schema: `Payment` (method enum `CASH | TRANSFER | QRIS | INSURANCE`, amount, paidAt, cashier userId). Partial payments out of scope; one payment per invoice for v1. **Done.** `invoiceId` is `@unique` — the v1 scope stated as a constraint, and relaxing it later for partial payments is a dropped index, not a rewrite. A payment recorded in error follows the invoice correction path (void + reissue → fresh invoice → fresh payment), so the row itself has **no `deletedAt`**: money that changed hands is permanent, exactly like a `DispenseRecord`. `cashierId` is `Restrict` for the dispensing-pharmacist accountability reason. `amount` must equal the invoice's `totalAmount`, but that is a cross-table rule left to the `P9-T03` service — the migration CHECK only rejects negatives, and zero stays legal so a fully discounted invoice still settles explicitly. `referenceNumber` (nullable) carries the external trace for non-cash methods (transfer slip, QRIS transaction id, insurance approval number). Indexes anticipate `P9-T04`: `(paid_at)` for the day range, `(method, paid_at)` for totals-by-method, `(cashier_id)` for per-cashier accountability. `PAYMENT_METHODS` lives in `#billing/schemas`; INSURANCE means manually recorded private payers — BPJS claims are not payments and arrive with Phase 11.
3. `P9-T03` Billing service/controller: generate invoice from a finished encounter (transactional), record payment, void with reason + audit. **Done.** New `billing` module with two controllers — `/service-tariffs` (list/create/update; tariffs deactivate, never delete, and `code` is immutable because invoice items snapshot provenance against it) and `/invoices` (list/get/generate/issue/payment/void). **Generation collects only what the visit already recorded** and prices it from the catalog: the consultation fee (one active CONSULTATION tariff auto-selected; several → the caller names one; none → skipped), procedures grouped by ICD-9-CM code and priced via `ServiceTariff.icd9cmCode`, and medications billed **from dispense records, not the prescription** — a partially dispensed prescription must not charge for the undelivered rest. Anything unpriceable becomes a `meta.gaps` entry (`NO_CONSULTATION_TARIFF | NO_TARIFF_FOR_PROCEDURE | UNPRICED_MEDICATION`), never a silent omission. Invoice number (`INV/YYYYMMDD/NNNN`, clinic-local day) is allocated from `InvoiceCounter` inside the same transaction as the insert. **Recording a payment makes the client repeat the amount** and rejects a mismatch with the stored total: a stale cashier screen fails loudly instead of settling the wrong bill; the payment insert and the PAID transition commit together. Void requires a reason, is refused for PAID (refunds out of scope, `INVOICE_STATUS_TRANSITIONS` is the single source), frees the encounter's live-invoice slot for a corrected reissue, and emits an `INVOICE_VOIDED` audit event (new `AuditAction` value) naming actor, previous status, and reason. Five ANY-only permissions (`service-tariff.read/write`, `invoice.read/write`, `payment.write`) granted to ADMIN — the kasir is the front desk in a pratama clinic; doctors and patients get no billing grant, and a patient-facing OWN read waits for the frontend phase. Seed ships three starter tariffs (`ON CONFLICT DO NOTHING`, unlike the reference catalogs — a reseed must never revert a clinic's repricing). Money moves through services as integer cents to keep float drift out of totals; `moneyAmountSchema` rejects >2-decimal amounts at the boundary.
4. `P9-T04` Daily cashier report endpoint (totals by method, by doctor) — the report clinic owners actually ask for first. **Done.** `GET /api/v1/reports/cashier-daily?date=YYYY-MM-DD` (defaults to the clinic's today), gated by the existing `invoice.read:any` — the report is an aggregate of data ADMIN already reads, so no new permission. **Built from payments only**: unpaid and voided invoices never appear (PAID is terminal, so a settled payment's invoice cannot have been voided afterwards), which makes the report exactly "what is in the drawer". The clinic-local day is converted to UTC bounds via the new `getStartOfCalendarDateInTimeZone` helper (inverse of `P8-T06`'s `getCalendarDateInTimeZone`; Jakarta's day D = `[D-1 17:00Z, D 17:00Z)`, proven in the unit spec) — `Payment.paidAt` is a timestamp, unlike the pre-stamped `queueDate`, so the boundary is derived at query time. Attribution runs payment → invoice → encounter → doctor; aggregation happens in the service over the day's rows (a pratama clinic day is small) with integer-cents sums so odd amounts cannot drift, lines sorted by revenue. Uses the `(paid_at)` / `(method, paid_at)` indexes laid down in `P9-T02`. Phase 9 backend complete; billing frontend lands with `P12-T01`.

## 5. Phase 10 - SATUSEHAT Integration (Backend, 6 Tasks)

Goal: FHIR R4 submission to Kemenkes. Build as an infrastructure adapter in `src/common/` or a dedicated `satusehat` module; domain services never import FHIR types. Develop entirely against the public sandbox first.

1. `P10-T01` Adapter foundation: OAuth2 client-credentials token client with caching/refresh, typed `ConfigService` config (base URL, org ID, per-environment client id/secret), timeout/retry/circuit-breaker (same policy pattern as the AI chatbot adapter in [ai-chatbot.md](./ai-chatbot.md)). **Done.** Lives in `apps/api/src/common/satusehat/` (common infrastructure, not a feature module — it has no API surface until `P10-T06`); feature modules inject `SatusehatHttpClient` only. Config follows the storage/MRN resolver pattern with **URL defaults pointing at the staging sandbox** (`api-satusehat-stg.dto.kemkes.go.id`, the environment the platform docs call sandbox) so production is always an explicit override; the three credential values (`SATUSEHAT_ORGANIZATION_ID`/`CLIENT_ID`/`CLIENT_SECRET`) must be set together or omitted together, and an unconfigured deployment **boots normally** — calls fail with a typed `SATUSEHAT_NOT_CONFIGURED` error instead of crashing startup, because most dev/CI environments have no Kemenkes registration. `SatusehatTokenClient` caches the Apigee token (`expires_in` arrives as a *string* — parsed tolerantly), refreshes inside a 60s pre-expiry safety window, and collapses concurrent refreshes into one upstream request; a 401 mid-flight invalidates the cache and the HTTP client replays once with a fresh token. Resilience per the ai-chatbot policy: per-request timeout via `AbortSignal.timeout` (Node's `DOMException` is not `instanceof Error`, so transport mapping checks `error.name` structurally), exponential-backoff retry **only for idempotent methods** (GET/PUT/DELETE) and only on transport-shaped failures (timeout, network, 429, 5xx) — never on 401/403 or business rejections — and a circuit breaker over consecutive transport failures with a single half-open probe. 4xx responses are recorded as breaker *successes*: they prove the upstream is reachable, which is all the breaker measures, and a probe that didn't record would deadlock the half-open state. Upstream failures map to `SATUSEHAT_UNAUTHORIZED | SATUSEHAT_TIMEOUT | SATUSEHAT_UNAVAILABLE | SATUSEHAT_CIRCUIT_OPEN | SATUSEHAT_REQUEST_REJECTED`; messages never carry credentials, tokens, or payloads.
2. `P10-T02` Master-data lookups: Patient by NIK -> store IHS number on `PatientProfile`; Practitioner by NIK/STR -> store IHS number on `DoctorProfile`. **Done.** `SatusehatMasterDataClient` joins the common adapter (`GET /{Patient|Practitioner}?identifier=https://fhir.kemkes.go.id/id/nik|{nik}`, returning bare IHS numbers so FHIR bundle shapes never leave the adapter); **practitioner resolution is NIK-based** — STR is not a search parameter the platform's FHIR API supports, it only matters at Kemenkes registration time. API surface is a new **`satusehat` feature module** (named `SatusehatIntegrationModule`; the P10-T04/T06 pipeline and ops surface land here): `POST /api/v1/satusehat/{patients|doctors}/:id/link`, gated by a new ADMIN-only `satusehat.link:any` permission — linkage is a front-desk identifier operation, not a clinical one. **Linking is idempotent and never re-resolves**: an IHS number is permanent, so an already-linked profile returns its state without an upstream call, and a re-link that could contradict the stored value is impossible by construction. The repository is the only layer touching ciphertext (per the `P7-T07` rule): it decrypts the NIK for the outbound query and seals the resolved patient IHS with `encryptSealedIdentifier`; the doctor IHS stays plaintext per the `P7-T03` schema decision. Responses follow the same asymmetry — the patient link result only confirms presence (`hasSatusehatPatientId`; the value is revealed solely via the audited unmask route), while the doctor result carries the pseudonymous practitioner id. A missing NIK is 422, no upstream match is 404, and adapter failures map to 503 (`SATUSEHAT_NOT_CONFIGURED`) / 502 (unreachable, rejected credentials) so front-desk staff can tell "fix the data" from "try again later". Each successful link emits a new `SATUSEHAT_PATIENT_LINKED` / `SATUSEHAT_DOCTOR_LINKED` audit event (enum migration) naming actor and profile, never identifier values.
3. `P10-T03` FHIR mappers: Encounter (registration/encounter lifecycle -> arrived/in-progress/finished), Condition (Diagnosis -> ICD-10), Observation (vitals -> LOINC-coded). **Done.** `SatusehatFhirMapper` joins the common adapter as pure translation — no I/O, no persistence; domain services hand it plain records and IHS numbers, and only the `P10-T04` pipeline ever sees the FHIR side. Cross-resource references (`Condition.encounter`, `Observation.encounter`, `Encounter.diagnosis`) are passed in as strings (`urn:uuid:` bundle-local or `ResourceType/{id}`) so transaction-bundle assembly stays with the caller. Encounter: identifier under `http://sys-ids.kemkes.go.id/encounter/{orgId}` valued with the local encounter UUID, class `AMB`, attender participant, and the platform-mandated `arrived → in-progress → finished` status history derived from registration `checkedInAt` / encounter `startedAt` / `endedAt` — a check-in stamped *after* the encounter opened (clock skew, backfill) is clamped to the encounter start so the platform never sees an inverted period; diagnosis references carry `rank` (PRIMARY = 1) with role `DD`. The mandatory `Location` reference exposed a config gap: new optional `SATUSEHAT_LOCATION_ID`/`SATUSEHAT_LOCATION_NAME` (the facility's Location resource is registered during platform onboarding), deliberately independent of the credential trio since it appears later in onboarding — Encounter mapping enforces it at map time with a typed `SATUSEHAT_NOT_CONFIGURED` error. Condition maps the signed `code`/`display` **snapshot** (never a catalog re-read) as `active` / `encounter-diagnosis` under `http://hl7.org/fhir/sid/icd-10`. Observations: one resource per measured column per vitals row (nulls skipped — a sparse front-desk row submits exactly what was measured), category `vital-signs`, LOINC/UCUM pairs fixed in an adapter-local table (8302-2 cm, 29463-7 kg, 8480-6/8462-4 mm[Hg], 8867-4 and 9279-1 /min, 8310-5 Cel, 2708-6 %) — the DB stores no codes by design (`P8-T02`), so a coding correction is an adapter change, not a migration. Timestamps are emitted as UTC instants (`Z`), which FHIR defines as equivalent to any offset form. BMI is not submitted: it is derived, and SATUSEHAT computes its own from the height/weight observations.
4. `P10-T04` Submission pipeline: outbox table (`SatusehatSubmission` with status/attempts/lastError) + async worker so clinical flows never block on Kemenkes availability; submit encounter bundle on encounter close. **Done.** One outbox row per encounter (`encounterId` `@unique`), created **inside the same transaction** as the FINISHED close in `EncounterRepository.closeEncounter` — deliberately writing another module's table there, because the outbox guarantee is precisely that a closed visit and its reporting-queue entry commit or roll back together (proven against real Postgres in `satusehat-submission-outbox.integration.spec.ts`, including the rollback case); cancelled encounters enqueue nothing. **The row carries scheduling state only, no payload snapshot**: the bundle is rebuilt from the live clinical record at send time, so a diagnosis retracted between close and submission is reported as corrected, not as signed. The worker (`SatusehatSubmissionWorker`) is a plain interval poller — no new scheduler dependency; single-instance monolith, per-row backoff state in the table so restarts lose nothing — that starts only when the adapter is configured **and** `SATUSEHAT_WORKER_ENABLED` is true, so dev/CI boot with no background activity. Processing (`SatusehatSubmissionService`, reused by the `P10-T06` retry surface) posts one FHIR **transaction bundle** per encounter — Encounter + Conditions (PRIMARY ranked 1) + Observations from the **newest** vitals row, wired by `urn:uuid:` bundle-local references — to the FHIR base root, and stores the returned IHS Encounter id as provenance. **Unlinked profiles are auto-linked by NIK at submission time** (reusing the `P10-T02` repository + master-data client, audited with a null actor and `trigger: SUBMISSION_WORKER`), so the front desk never has to pre-link manually. Failure taxonomy: transient upstream errors (timeout/unavailable/circuit-open) reschedule with exponential backoff (base `SATUSEHAT_SUBMISSION_RETRY_BASE_DELAY_MS`, doubling per attempt) up to `SATUSEHAT_SUBMISSION_MAX_ATTEMPTS`; data problems (no NIK, no MPI match, encounter not finished) and permanent upstream rejections (401/403, FHIR validation) park the row FAILED immediately with a readable `lastError` — retrying cannot fix data, and a 401 loop would burn the attempt budget that a later credential fix still needs.
5. `P10-T05` Medication resources: MedicationRequest/MedicationDispense from prescription + dispense records using `kfaCode` (skip items without a KFA code, log a gap report). **Done.** Three new mapper methods join `SatusehatFhirMapper` and the `P10-T04` bundle grows Medication → MedicationRequest → MedicationDispense entries, all inside the same per-encounter transaction bundle. **Medication** is deduplicated per catalog item (one entry even when prescribed and dispensed), KFA-coded under `http://sys-ids.kemkes.go.id/kfa` with the local catalog `code` as the org-scoped identifier and the mandatory `MedicationType` extension (`NC` — the catalog holds products, not compounds; racikan support would need a compound model first). **MedicationRequest** — one per prescription line on the visit's ISSUED/PARTIALLY_DISPENSED/DISPENSED prescriptions (DRAFT is unsigned, CANCELLED is withdrawn) — carries the dual identifier (`prescription/{org}` + `prescription-item/{org}`), `status completed`/`intent order`, the doctor as requester, and **textual dosage only** (`dosage, frequency, instructions` joined): the record stores free-text dosing, and inventing structured FHIR timing from prose would assert precision the record does not carry; `substitution.allowedBoolean false`. **MedicationDispense** — one per dispensed line from DISPENSED dispense records — is **performed by `Organization/{orgId}`, not a Practitioner**: the pharmacist is a system user without an IHS number, and naming the attending doctor would falsify who handed the medication over; `authorizingPrescription` wires to the matching MedicationRequest entry by `(prescriptionId, medicationId)` when one exists, and `whenHandedOver` is the dispense timestamp. **Items whose catalog row lacks `kfaCode` are skipped, never guessed**, and every submission logs a gap report naming each skipped `code (name)` once — the fix is `P7-T05`'s medication-update endpoint, not a fabricated code. Billing (`P9`) intentionally differs: an unpriced item becomes a visible invoice gap entry, an uncoded one only a log line, because money must reconcile per-visit while KFA coverage is a catalog-wide hygiene task.
6. `P10-T06` Ops surface: submission status endpoint + retry endpoint for admins; integration tests against recorded sandbox fixtures. **Done.** Two endpoints join the `satusehat` feature module: `GET /api/v1/satusehat/submissions` (paginated, newest first, filterable by `status`/`encounterId`) and `POST /api/v1/satusehat/submissions/:id/retry`, gated by two new ADMIN-only permissions (`satusehat.submission.read:any` / `satusehat.submission.retry:any`) — read and retry are split because watching the queue is monitoring while retrying re-opens work, and the `P11-T07` integrations monitor should not need the mutating grant. The list exposes **scheduling state only** — the outbox stores no payload snapshot (`P10-T04`), so nothing clinical and no identifier beyond the local encounter UUID can leak through the ops surface. **Retry accepts only FAILED rows** (SUBMITTED and still-queued PENDING rows return 409: one is done, the other needs no help), resets the attempt budget to zero — the budget rationed the *old* failure cause; a fixed root cause deserves the full backoff schedule — and then **processes the row synchronously through the same `SatusehatSubmissionService` the worker uses**, so the admin sees the real outcome in the response (SUBMITTED with the IHS encounter id, PENDING with a scheduled retry, or FAILED again with a fresh readable `lastError`) instead of waiting a poll cycle; the previous `lastError` survives the requeue until the next attempt overwrites it. Each retry emits a new `SATUSEHAT_SUBMISSION_RETRIED` audit event (enum migration) naming the actor and the prior attempt count. Integration coverage (`satusehat-submission-ops.integration.spec.ts`) runs the token client, HTTP client, FHIR mapper, and submission service **for real against recorded staging-sandbox fixtures** stubbed at the `fetch` transport (Apigee token payload with string `expires_in`, a `transaction-response` bundle with `_history`-suffixed entry locations, OperationOutcome rejections) — proving the retry path end to end: bundle assembly, bearer auth, IHS id extraction on success, permanent settle on a 400 rejection, and backoff reschedule on a 503.

## 6. Phase 11 - BPJS PCare Bridging (Backend + Frontend, Scoping + 7 Tasks)

Goal: serve JKN clinics (the majority of klinik pratama). Highest external-dependency risk — PCare credentials are issued per facility and the API has its own conventions (custom signature headers, AES+LZ-String encrypted responses, non-FHIR payloads, BPJS-specific code systems). Start with a scoping spike.

Full design: [bpjs-pcare.md](./bpjs-pcare.md) — read before starting `P11-T01`.

1. `P11-T01` Spike: obtain PCare dev credentials; confirm auth headers (cons id / timestamp / HMAC signature / X-Authorization / user key) and the response decrypt routine (AES + LZ-String) against the dev environment; map required flows: peserta (eligibility), pendaftaran, kunjungan, obat, rujukan. Output: working codec utility with recorded fixtures + ADR in `docs/post-mvp/decisions.md`. **Done** (ADR D-022), with one deliberate substitution: dev credentials are facility-issued via the BPJS branch office and unobtainable without a pilot clinic, so the protocol was confirmed against **two independent community reference implementations that agree exactly** (antmey/bridging-bpjs, fadlyyy/bpjs-pcare) instead of the live dev environment, with the HMAC and AES layers additionally cross-checked byte-for-byte against the openssl CLI. Codec lands as pure functions in `apps/api/src/common/bpjs-pcare/` — `buildBpjsPcareHeaders` (five headers; `kdAplikasi` is the fixed `095`) and `decodeBpjsPcareResponse` (AES-256-CBC under SHA-256(`consId+secretKey+timestamp`), IV = first 16 hash bytes, then LZ-String `decompressFromEncodedURIComponent`, then JSON) — plus typed `BpjsPcareCodecError` with a three-way failure taxonomy (malformed / decrypt / decompress) so `P11-T02` can tell a timestamp-reuse bug from upstream garbage. **The response key is derived from the request timestamp**, so the adapter must hold one timestamp per request across send and decode — the core constraint the `P11-T02` interceptor is designed around. Error envelopes arrive unencrypted and pass through undecoded; `metaData.code` is string-or-number and normalisation is deferred to the adapter. New dependency: `lz-string` (the reference JS implementation the PHP ports derive from). Rujukan turned out to ride on the kunjungan payload (no standalone create endpoint) — full endpoint map in the ADR. First action when pilot-clinic credentials arrive: run the `P11-T02` test-connection read and re-record the pinned fixtures from a real response.
2. `P11-T02` `BpjsPcareConfig` schema (per-facility, nullable `facilityId`) with AES-256-GCM credential encryption reusing the `P7-T07` crypto pattern; adapter foundation (signature interceptor, codec, timeout/retry/circuit-breaker); admin CRUD with write-only secrets + test-connection endpoint; `bpjs.config.manage` permission. **Done.** `bpjs_pcare_configs` stores the non-secret identifiers plaintext and the three secrets sealed by a new `BpjsCredentialCryptoService` (same AES-256-GCM layout as the P7-T07 service, dedicated `BPJS_CREDENTIAL_ENCRYPTION_KEY`, no blind index — credentials are never looked up by value). **The key is optional at boot**, unlike the PII keys: most deployments have no BPJS bridging, so a missing key fails credential operations with a 503, not startup. `facilityId` stays nullable-unique for multi-tenancy, and because Postgres treats NULLs as distinct there, a hand-written partial unique index on `(facility_id IS NULL)` is what actually enforces the single-tenant singleton. The adapter (`apps/api/src/common/bpjs-pcare/`) grows `BpjsPcareHttpClient` on the P11-T01 codec: **credentials travel per request** (they are database rows, not deployment config — the structural difference from the SATUSEHAT adapter), each attempt signs with a fresh timestamp and decodes with that same timestamp, retries are idempotent-only with exponential backoff, and the circuit breaker counts transport failures while recording PCare's business rejections (`metaData` codes, carried through with BPJS's own readable message) as reachability successes. Base URLs resolve per `environment` enum with env-var overrides — the dev host has varied across BPJS issuance eras, so it must be confirmed per facility. Feature module `modules/bpjs-pcare/` ships the singleton surface `GET|PUT|DELETE /api/v1/bpjs/config` + `POST /api/v1/bpjs/config/test-connection` behind ADMIN-only `bpjs.config.manage:any`: secrets are write-only end to end (requests may carry them, views show `has*` flags + last-4 only, an update that omits them keeps the stored values, first save requires all three), the repository is the sole encryption boundary (seal on write, decrypt only into the ephemeral per-call connection), and every create/update/delete/test emits a `BPJS_CONFIG_*`/`BPJS_CONNECTION_TESTED` audit event naming changed fields, never values. **Test Connection reads `poli/fktp/0/1` and reports failure as a 200 outcome** (persisted to `lastTestedAt`/`lastTestResult`) so misconfiguration surfaces in Settings, not mid-registration. Integration spec proves the full seal → store → reveal → sign → decode chain against a fetch stub that verifies the HMAC and encrypts with the request's own timestamp; key-rotation procedure in [deployment-runbook.md](../ops/deployment-runbook.md) §5.3.
3. `P11-T03` Reference-data sync (poli, dokter, kesadaran, tindakan, diagnosa, DPHO, spesialis, sarana) into local tables + mapping surfaces: `DoctorProfile.bpjsDoctorCode`, poli mapping, `Medication.dphoCode`. Submissions must fail fast with a readable message when a mapping is missing. **Done**, with one deliberate substitution: the design doc's eight per-catalog tables carry an identical shape (code, display, `syncedAt`), so they land as **one enum-keyed `bpjs_reference_items` table** (`BpjsReferenceCatalog` enum, unique `(catalog, code)`, a `groupCode` qualifier holding TINDAKAN's kdTkp bucket) — the sync, search, and mapping-validation surfaces stay generic instead of being stamped out eight times. The catalogs split by how PCare serves them: the six enumerable ones (POLI, DOKTER, KESADARAN, TINDAKAN, SPESIALIS, SARANA) are replaced **wholesale in one transaction per catalog** by `POST /api/v1/bpjs/reference/sync` (paginated fetch plans pinned in the adapter's descriptor map; TINDAKAN iterates kdTkp 10/20/50), while DIAGNOSA and DPHO have **keyword-only upstream endpoints and cannot be enumerated**, so they populate incrementally through `POST /api/v1/bpjs/reference/{catalog}/search` (live lookup, results upserted into the cache). Dropdowns and mapping screens read only the local table (`GET /api/v1/bpjs/reference/{catalog}`, plus a per-catalog `status` endpoint with `lastSyncedAt` and an `isSyncable` flag for the settings screen) — never live BPJS calls. Wire shapes stay in the adapter: a defensive parser normalises PCare's `{count, list}` envelopes (string-or-number counts, per-catalog field names) and **fails loudly as RESPONSE_MALFORMED when an entry lacks its code/display field**, so a BPJS-side rename cannot silently empty a catalog. Mapping surfaces land as `PUT /api/v1/bpjs/mappings/{doctors|specialties|medications}/:id` (set-or-clear; a non-null code must exist in the synced catalog and is rejected with a readable message pointing at the sync — a typo surfaces at mapping time, not as a rejected pendaftaran with a patient waiting). The poli mapping resolves the design doc's open question onto **`Specialty.bpjsPoliCode`**: no standalone poli entity exists and a registration reaches BPJS through its doctor's specialty, so Specialty is the structural equivalent. `Medication.dphoCode` is unique for the same reason `kfaCode` is (one catalog identity, at most one local row; a concurrent double-link settles as 409 via the DB constraint), and the medication list view now carries it read-only. Three new ADMIN-only permissions: `bpjs.reference.sync:any` (bulk sync + keyword lookups — both hit the live PCare API under stored credentials), `bpjs.reference.read:any` (split off so the `P11-T07` integrations monitor can watch catalogs without the mutating grant), and `bpjs.mapping.manage:any` (a wrong mapping mis-codes every later claim). Every sync and mapping change audits (`BPJS_REFERENCE_SYNCED` with per-catalog counts, `BPJS_MAPPING_UPDATED` naming the code). Integration spec (`bpjs-reference.integration.spec.ts`) runs the repository, crypto, HTTP client, signing, and codec for real against a signature-verifying fetch stub that encrypts each reply with that request's own timestamp — proving sign → decode → parse → replace for every enumerable catalog, the DPHO search-and-cache path, and that mapping validation really gates on what was synced. The fail-fast groundwork for `P11-T05` submissions is the nullable columns plus validated writes: the submission builder refuses on a null mapping with a readable message instead of sending garbage.
4. `P11-T04` Eligibility check by BPJS number / NIK at registration check-in. Synchronous (front desk needs it immediately), cached per patient per day, degrades to an explicit "BPJS unreachable" state rather than blocking registration. **Done.** `POST /api/v1/bpjs/eligibility/patients/:patientId/check` (new front-desk permission `bpjs.eligibility.check:any`, ADMIN-only — the check reveals membership PII, so it stays off DOCTOR/PATIENT) resolves the lookup identifier from the patient profile — **the sealed BPJS number, falling back to NIK** (`peserta/{noka}` / `peserta/nik/{nik}`), decrypted only inside the repository for the outbound path and never echoed anywhere; a patient with neither is a readable 400 pointing at the profile. The check is **deliberately a standalone endpoint, not a hook inside the registration transaction**: wiring it into registration-create would make check-in latency depend on BPJS, which is exactly what the "never block registration" constraint forbids — the front desk fires it from the eligibility card (`P11-T07`) with the patient at the counter. Definitive outcomes (ACTIVE / INACTIVE with BPJS's own readable `ketAktif` reason / NOT_FOUND carrying the upstream rejection message) are **cached one row per patient per clinic-local day** (`bpjs_eligibility_checks`, unique `(patientId, checkedDate)`, `CLINIC_TIMEZONE` day boundary — the same reasoning as the queue-board day) so repeat check-ins never hammer PCare; `force: true` bypasses the cache after the front desk corrects patient data. **UNREACHABLE is a 200 outcome, never an error and never cached**: transport/auth/codec failures degrade to an explicit state whose message says registration can proceed, and the next attempt always retries upstream. A PCare business rejection (`REQUEST_REJECTED`) settles as a cached NOT_FOUND with BPJS's message, distinct from reachability failures. The card payload mirrors the design's §6 card: member name, type, class, registered-FKTP code/name plus a computed `isRegisteredHere` (compared against the stored `kdProviderPpk`), Prolanis/PRB flags — **and no card number**, which never leaves the patient profile. The adapter grows a tolerant peserta parser (bare object / `{peserta}` / `{list}` envelope variants, string-or-boolean `aktif`, string flag coercion) that fails loudly as RESPONSE_MALFORMED when a member object carries no activity signal — an eligibility card must never guess. Every live check audits (`BPJS_ELIGIBILITY_CHECKED` with state, identifier type, and whether it was forced); cache hits don't re-audit. Integration spec (`bpjs-eligibility.integration.spec.ts`) seals a real BPJS number with the identifier crypto, then proves decrypt → sign → lookup → decode → cache end to end against a signature-verifying fetch stub, plus the day-cache/force paths and the uncached UNREACHABLE degrade.
5. `P11-T05` Submission pipeline: `BpjsSubmission` outbox (mirrors `SatusehatSubmission`) + async worker; submit `pendaftaran` on check-in and `kunjungan` on encounter close; status on registration/encounter; retry endpoint; propagate HMS-side cancellation as `pendaftaran` DELETE. **Done.** `bpjs_submissions` mirrors the SATUSEHAT outbox (PENDING/SUBMITTED/FAILED with FAILED terminal until admin retry, attempts, `nextAttemptAt` backoff, no payload snapshot — builders re-read the clinical record at send time) with two structural differences: a **`type` enum (PENDAFTARAN / KUNJUNGAN / PENDAFTARAN_DELETE) keyed on the registration** for all three flows (the kunjungan reaches its encounter through the 1:1 relation; unique `(registrationId, type)` is the idempotency guarantee), and **`bpjsReferenceNo` + `submittedKdPoli` columns** — the returned noUrut/noKunjungan, and the poli code the pendaftaran actually went out with, because the DELETE path must name that exact code even if the admin remaps the specialty in between. Enqueues are transactional inside the host repositories (the P10-T04 justification verbatim): check-in → PENDAFTARAN in `RegistrationFlowRepository.updateRegistration`, FINISHED close → KUNJUNGAN next to the SATUSEHAT enqueue in `EncounterRepository.closeEncounter` — both **only when the patient has a stored BPJS number and bridging is configured active**, so non-JKN visits never enter the outbox. Cancellation (both paths: registration PATCH and encounter cancel) enqueues PENDAFTARAN_DELETE **only when the pendaftaran already reached PCare**; an unsent one is failed by the builder's own registration-status guard instead (nothing upstream needs revoking), and the in-flight race — cancelled while the worker was sending — is closed by the service re-checking registration status after a successful pendaftaran and enqueueing the delete itself. Failure classification mirrors SATUSEHAT (permanent = `BpjsSubmissionDataError` or NOT_CONFIGURED/UNAUTHORIZED/REQUEST_REJECTED; else exponential backoff, 8 attempts × 60s base, env-tunable) with **one deliberate delta: a walk-in checked in without an appointment has no doctor yet, so an unresolvable poli at pendaftaran time is a *transient* error** — the doctor arrives when the encounter opens, so time fixes it where the retry budget allows; missing mappings (kdPoli, kdDokter), a missing primary diagnosis, and cancelled registrations fail fast and permanently with messages written for the monitor — the `P11-T03` fail-fast requirement made real. The kunjungan additionally **waits transiently while its pendaftaran is still PENDING** and fails permanently if the pendaftaran FAILED (fix that first). Payload builders are pure adapter functions (`kdTkp` '10' outpatient, `kdSadar` '01' — no consciousness level is modelled clinically, `kdStatusPulang` '3' berobat jalan until `P11-T06` rujukan overrides it, vitals from the latest encounter reading with zeros for unmeasured values, diagnoses PRIMARY-first capped at three); like the rest of the protocol, field-level shapes follow the two agreeing D-022 reference implementations with live confirmation deferred to pilot credentials. Worker mirrors the SATUSEHAT poller (15s interval, batch 5, overlap-skip, per-row error isolation, `BPJS_WORKER_ENABLED` gate — no bootstrap credential check, since credentials are DB rows and the enqueue hooks already gate). Ops surface `GET /api/v1/bpjs/submissions` (paginated, filterable by status/type/**registrationId — which is how bridging status chips on a registration or encounter read their state**, rather than new fields on those modules' views) + `POST /api/v1/bpjs/submissions/:id/retry` (FAILED only, 409 otherwise, attempt budget reset, synchronous processing so the admin sees the settled outcome, `BPJS_SUBMISSION_RETRIED` audit) behind ADMIN-only `bpjs.submission.read:any` / `bpjs.submission.retry:any`, split like the SATUSEHAT pair. **Obat (DPHO-coded dispense) submission is deferred to `P11-T06`**: PCare takes medications as separate `obat/kunjungan` POSTs after the kunjungan returns its noKunjungan, so it rides the same encounter-close row once the rujukan work touches that flow. Two integration specs: the outbox guarantee against real Postgres (check-in/close/cancel enqueue semantics, non-BPJS visits enqueue nothing), and the ops surface through the real decrypt → sign → build → codec pipeline against a signature-verifying fetch stub (retry settles SUBMITTED with the decoded noUrut; a PCare business rejection settles FAILED with BPJS's readable reason).
6. `P11-T06` Rujukan (referral) issuance from encounter close + monthly reconciliation report (tercatat vs terkirim vs gagal) for the claim deadline. **Done**, together with the obat submission deferred from `P11-T05`. **Rujukan capture is clinical data, so it lives in the emr module**, not the BPJS module: `PUT|GET|DELETE /api/v1/encounters/:id/bpjs-referral` sits beside vitals/diagnoses behind the same `encounter.write` gate and `EncounterAccessService` ownership machinery — the attending doctor records the referral while the encounter is open (destination FKRTL `kdppk`, subspesialis and/or khusus/TACC code, optional sarana, planned referral date, notes; one per encounter, soft-deleted, upsert revives). PCare has no standalone rujukan create (D-022) — **the submission service folds the stored referral into the kunjungan payload at send time**, flipping `kdStatusPulang` from '3' (berobat jalan) to '4' (rujuk lanjut) and attaching the `rujukLanjut` block; referral codes are sent as recorded because the subspesialis catalog is per-specialty and not fully synced, so PCare is the validator of record. **Obat lands as a fourth outbox type**: an encounter-linked dispense for a BPJS patient transactionally upserts the visit's OBAT row inside `PharmacyFlowRepository.createDispense` (same outbox guarantee; the upsert is a no-op when the row exists, so a follow-up dispense never re-opens a settled one). The OBAT builder **waits transiently for the kunjungan's noKunjungan** (the same chain discipline as kunjungan-waits-for-pendaftaran; a FAILED kunjungan fails it permanently with a fix-that-first message), then posts one `obat/kunjungan` per DPHO-mapped dispensed item — signa parsed from the prescription's free-text "3x1" convention with a 1×1 fallback, quantity from the dispense line — **skipping unmapped medications with a warning** (the SATUSEHAT KFA-gap philosophy) and failing readably when none are mapped. The reconciliation report `GET /api/v1/bpjs/reports/monthly?month=YYYY-MM` (behind `bpjs.submission.read:any`) answers the claim-deadline question per submission type: **tercatat (everything enqueued for visits whose clinic-local day falls in the month — scoped by the visit's queueDate with checkedInAt fallback, because the claim month is the visit month, not the retry month), terkirim (SUBMITTED), gagal (FAILED)** plus still-pending, and lists the failed rows (capped at 100, newest first, with their monitor-readable reasons) so an admin can chase mappings and retries before the window closes. Coverage: the outbox integration spec gains the dispense→OBAT transactional-enqueue case against real Postgres; unit specs cover the rujuk-lanjut payload flip, obat chaining/skip/signa semantics, and the month-boundary aggregation (including the December→January rollover). With this, the Phase 11 backend is complete through T06 — `P11-T07` (frontend surfaces) and the `P11-T08` antrean-online evaluation remain, and the first live-credential action is unchanged: re-record the pinned fixtures via test-connection, then confirm the pendaftaran/kunjungan/obat field shapes (D-022's deferred confirmation).
7. `P11-T07` Frontend: BPJS settings page, mapping screens, eligibility card at registration, bridging status chips, and a **shared Integrations monitor** covering both SATUSEHAT (`P10-T06`) and PCare submissions. May be folded into `P12-T01`. **Done.** The admin shell now exposes an RBAC-filtered `/admin/integrations` route with three capability-scoped surfaces: a shared SATUSEHAT/PCare submission monitor (provider and status filters, BPJS submission-type filters, terminal-failure retry actions, and the monthly tercatat/terkirim/pending/gagal reconciliation), a write-only BPJS credential lifecycle (create/update with secret retention, masked last-four indicators, connection test, activation, and removal), and local doctor/specialty/medication mapping screens backed by synchronized PCare reference catalogs plus live DPHO search-and-cache. Registration rows carry a PCare outbox-status chip and a synchronous eligibility dialog that distinguishes live vs daily-cache results, shows the non-sensitive membership/FKTP/program fields, supports a forced refresh, and preserves the P11-T04 non-blocking UNREACHABLE state; neither surface displays a BPJS card number or clinical outbox payload. Frontend CASL now understands the backend's `bpjs.*` and `satusehat.*` actions/resources, gates the route on the server before render, filters tabs/actions independently, and keeps unauthorized registration rows query-free. The checked-in OpenAPI contract was refreshed from the running API and Orval regenerated the BPJS/referral client surface; frontend coverage verifies integration permission parsing and navigation visibility alongside the existing registration-row suite.
8. `P11-T08` Antrean online (Mobile JKN queue) bridging — evaluate after core PCare flows; queue-number model from `P8-T06` is the prerequisite. **Done as an evaluation** (ADR D-023, full analysis in [bpjs-antrean-online.md](./bpjs-antrean-online.md)): **adopt the feature, but not in Phase 11** — it moves to Phase 14 (§9) behind named external prerequisites. Antrean online is a second BPJS integration wearing the D-022 protocol, not a seventh PCare endpoint: it needs **separately issued Antrean-service credentials** (own consId/secretKey/userKey, own `antreanfktp` base URL, same AES+LZ-String decode, minus PCare's `X-Authorization`), and above all **it is bidirectional** — the facility must host *get token / status antrean / ambil antrean / sisa antrean / pasien baru / batal antrean* for BPJS to call, of which two are writes into bookings and patient master data reachable from the public internet. HMS has exactly two public routes today (`auth`, `health`) and neither writes, so that is a new security boundary, not a task appended to a finished phase — and unlike everything else in Phase 11 it **cannot be proven by fixtures**, because the contract is the facility's to publish and is confirmed only at BPJS's UAT (pakta integritas, plus a branch-office profile flag before Mobile JKN lists the clinic at all). The evaluation records the model gaps so they are not rediscovered: the `P8-T06` counter is keyed on date alone while antrean numbers are **per-poli** (split it, keeping the clinic-wide roll as the physical ticket — two numbers on purpose, because the paper roll is floor management and the antrean number is a BPJS contract); `AppointmentSession` is already a near-exact match for an HFIS shift with a quota, so a Mobile JKN booking lands as a **session join**, not a new appointment concept; the `P7-T06`/`P7-T07` sealed-NIK blind index gives `pasien baru` dedupe-before-create for free, but a BPJS-originated write has **no human actor**, so a system-actor/provenance convention is required — and it doubles as the flag that stops the outbox from re-publishing a Mobile JKN booking back to BPJS as a walk-in; HMS records **no "patient called" event** (`PENDING → CHECKED_IN → COMPLETED`), so whether the FKTP flavour wants FKRTL's task-ID vocabulary (`updatewaktu`/`getlisttask`) decides whether that is a real UX change or an encounter-open approximation — the spike's first question; and poli/doctor/shift/quota live in **HFIS, which HMS cannot write**, so drift is reconciled and reported, never synced. Nothing was built: the one piece that is buildable today with no BPJS dependency is the per-poli counter (`P14-T01`), and it is scheduled rather than smuggled in here.

## 8. Phase 13 - AI Chatbot Integration (Backend + Frontend, 11 Tasks)

Goal: integrate an external production AI service through the HMS backend gateway with strict safety boundaries. **Start only after Phase 10 SATUSEHAT submission pipeline is stable** (`P10-T06` complete) so patient/practitioner IHS linkage and encounter data can enrich chat context safely.

Full specification: [docs/post-mvp/ai-chatbot.md](./ai-chatbot.md).

1. `P13-T01` Schema migration: `AiProviderConfig`, `ChatSession`, `ChatMessage`, enums, indexes. **Done.** Three enums (`AiProviderKind`, `ChatChannel`, `ChatActor`) and three tables; no service code yet, so the guarantees that matter are the ones the database holds on its own. **Exactly one active provider config** is a hand-written partial unique index (Prisma cannot express one) over `COALESCE(facility_id, nil-uuid)` where the row is active and not soft-deleted — partial because staging an inactive replacement is how an admin cuts over, and `COALESCE`d because HMS ships single-facility, so today's rows carry `NULL` and Postgres would treat each of them as distinct. API keys land as ciphertext plus a four-character hint and a `credentialKeyVersion`, matching `BpjsPcareConfig` so one rotation runbook covers both. Sessions are `onDelete: Restrict` on their owner (a transcript is a record of what a patient was told; deleting the account must not erase it) while a message's author is `SetNull` (attribution can go, the turn cannot); messages carry no `updatedAt`/`deletedAt` because PMK 24/2022 retention needs the exact text that was shown. `ChatSession.providerKey` is a plain string, not an FK — configs get soft-deleted and the env fallback has no row at all. All six guarantees are proven against real Postgres in `ai-chatbot-schema.integration.spec.ts`.
2. `P13-T02` RBAC seed: chat + `ai-provider.*` permissions + role bindings. **Done.** The MVP baseline already carried four chat keys; this adds the five the Phase 13 surface actually needs — `chat.session.read:any`, `chat.session.read:own`, `chat.session.delete:own` (`ChatSession`), and the `ai-provider.read:any` / `ai-provider.write:any` pair over a new `AiProviderConfig` subject. Two calls depart from a literal reading of [ai-chatbot.md](./ai-chatbot.md) §7. **PHARMACIST gets nothing**: the table reads "all authenticated" for the OWN-scoped session reads, but the chatbot ships only a PATIENT and a DOCTOR channel, so a role that cannot create a session has no session to read or delete and the grant would never resolve a row — deny-by-default is cheaper to widen later than to claw back. **ADMIN deletes only its own**: it gets `chat.session.read:any` for the support view but not a delete counterpart, because `P13-T01` made `ChatSession.ownerUserId` `onDelete: Restrict` precisely so a transcript outlives its owner — removing someone else's is a retention job's decision, not a support action. Provider credentials stay ADMIN-only for the same reason `bpjs.config.manage:any` does (a stored key is spendable and picks which third party sees chat context), split read-from-write so a later ops surface can show which provider is live without holding the grant that rotates the key. SUPER_ADMIN picks all nine up through the catalog-wide union, as every role does. The frontend CASL mirror moves in step: `AiProviderConfig` joins `AppSubject`, `ai-provider` joins `SUBJECT_BY_RESOURCE`, and the admin preset gains the four capabilities. Coverage is a **static spec over `seed.sql`** (`ai-chatbot-rbac-seed.spec.ts`) rather than an integration spec, because CI runs `migrate deploy` and never seeds — there is no database in CI for an integration test to observe these rows in, and the seed file is the artifact that ships. It asserts each key's resource and scope (a typo in either silently changes who the guard lets through) and pins each role's grant set exactly, so a future permission cannot be added to a role here without a deliberate edit.
3. `P13-T03` Module skeleton + repositories (provider config CRUD with encrypted keys, session/message ownership filters). **Done.** `AiChatbotModule` registers in `AppModule` with two exported repositories and nothing else — services and controllers accumulate in T04/T05/T08. The **repository is the encryption boundary**, verbatim from the BPJS precedent: plaintext API keys are sealed inside `AiProviderConfigRepository`, ciphertext never leaves the file, and `getActiveConnection()` is the single decrypt point. That forced one deliberate pull-forward: `AiProviderCryptoService` (listed under T04) exists now, in `common/crypto` beside its BPJS twin rather than the doc's module-`infrastructure/` placement, because the global `CryptoModule` is this codebase's declared home for credential encryption and its repositories-only injection rule. Same AES-256-GCM sealed-value layout, dedicated `AI_PROVIDER_ENCRYPTION_KEY` (+ optional `AI_PROVIDER_KEY_VERSION`), optional at boot — a missing key fails key storage with a typed `AI_NOT_CONFIGURED`, not the deployment. A keyless config (self-hosted Ollama) stores empty ciphertext **without touching crypto at all**, so it works on deployments that never set the key; per-kind key-requiredness is a T05 service rule. Config rows are created staged-inactive; `activateConfig` swaps the active slot transactionally under the P13-T01 partial unique index, and soft delete releases the slot in the same write. `ChatRepository` enforces ownership **in the queries themselves**: `findSessionForOwner` / `softDeleteSessionForOwner` carry `ownerUserId` in the WHERE clause so a foreign session id reads as not-found, and the `:own` list method makes the owner mandatory by type while the admin support view is a separate method — an omitted owner is a compile error, not a data leak. Messages have create and read only (no update or delete exists anywhere, the append-only guarantee made structural), history pages by cursor over the `(sessionId, createdAt)` index, and a soft-deleted session's transcript stays readable for audit. One schema truth surfaced by the integration spec: `createdAt` has millisecond precision and the UUID id is no tie-break, so two appends in the same millisecond have no defined order — `AppendChatMessageData.createdAt` now lets the writer stamp turn order, which the T05 orchestration must use so a user turn and its assistant reply never flip. Shared types land in `packages/shared-types/src/ai-chatbot/` (`schemas.ts` enum values mirroring the Prisma enums, `types.ts` repository records/payloads — records carry `hasApiKey` + hint, never ciphertext or plaintext); `contracts.ts` waits for the API surface. Coverage: a crypto unit spec mirroring the BPJS one, and a 13-case integration spec against real Postgres (seal/round-trip/rotation, keyless Ollama on an unconfigured deployment, atomic slot swap, and the full ownership matrix).
4. `P13-T04` Multi-provider layer: `AiChatProvider` interface, `AiProviderRegistry`, `OpenAiCompatibleAdapter`, `AnthropicAdapter`, resolver + crypto + per-config circuit breaker. **Done** (crypto had already landed with `P13-T03`). The layer splits into pure translators and one resilient executor. **`AiProviderHttpClient`** owns the whole cross-cutting policy so adapters never see it: per-call timeout from the clinic's config, a circuit breaker **per `configId`** (the SATUSEHAT/BPJS breaker verbatim, but mapped per key — one clinic's dead upstream or bad credential cannot trip another's circuit, and the env-fallback sentinel `platform-env` gets its own), and a deliberately narrow retry: only "the request never got out" (DNS/connection-refused) is retried, once by default — **a timeout is never retried** because the completion may already be processing and a chat user is waiting synchronously, and any delivered HTTP status is an answer, not a transport failure. Any HTTP response records the upstream reachable, so a 401 flood cannot open a circuit. **`OpenAiCompatibleAdapter`** covers five kinds through small wire-strategy objects (bearer for OPENAI/DEEPSEEK/OLLAMA/OPENAI_COMPATIBLE with the header simply omitted for a keyless Ollama; Azure gets its deployment-in-URL path, `api-version` query, and `api-key` header); **`AnthropicAdapter`** is separate because Claude wants the system prompt as a top-level field, `x-api-key` auth, and content blocks — both normalize to the same result type, so orchestration cannot tell vendors apart. Upstream failures map through one shared function: 401/403 → `AI_PROVIDER_UNAUTHORIZED`, model-shaped 400/404/422 → `AI_PROVIDER_MODEL_NOT_FOUND` (detected by the vendor's error text; a 404 without model talk is a wrong base URL → `AI_PROVIDER_UNAVAILABLE`), everything else → `AI_PROVIDER_UNAVAILABLE`, with the vendor's own readable reason carried through — the BPJS `metaData.message` precedent, because the admin fixing a config needs the vendor's words. **`AiProviderRegistry`** maps kind → adapter and answers a miss with typed `AI_NOT_CONFIGURED` instead of a crash. **`AiProviderResolverService`** turns "whatever is configured" into a callable `{adapter, config}`: active row through the repository's single decrypt point, else the `AI_PLATFORM_*` env fallback (kind + model required to activate it), then the per-kind rules the repository deliberately doesn't know — vendor-default base URLs (explicit URL *required* for OPENAI_COMPATIBLE/AZURE_OPENAI), key requiredness (OLLAMA exempt), and a model-id allowlist pattern so a config can never smuggle URL syntax into an adapter's request path. Every rejection is `AI_NOT_CONFIGURED`. `contextPayload` and `sessionExternalId` ride the normalized input but v1 adapters keep them off the wire — context is folded into `messages` by the T05 orchestrator. Coverage: 49 unit cases across six specs — breaker state machine, retry/no-retry/circuit-isolation against a stubbed `fetch`, both adapters' wire shapes and error tables, registry routing for all six kinds, and the resolver's full validation matrix.
5. `P13-T05` Admin provider API (CRUD, activate, test connection) + `AiChatbotService` orchestration. **Done.** `/api/v1/admin/ai-providers` (list, create, PATCH, activate, test, DELETE) behind `ai-provider.read:any` / `.write:any`, plus the exchange orchestration the T08 controller will expose. **API keys stay write-only end to end**: requests may carry one, views return only `hasApiKey` + the four-character hint, an omitted `apiKey` on PATCH keeps the stored ciphertext and a present one rotates it, and every mutation audits *changed field names* — never values — through five new `AuditAction` enum values (migration `20260811000000`). Per-kind requiredness is enforced **at write time, not just at call time**: the same rules the resolver applies (key required except `OLLAMA`, explicit base URL for `OPENAI_COMPATIBLE`/`AZURE_OPENAI`) run on create, on a `baseUrl: null` clear, and again on **activate** — activating a config the resolver would reject would take chat down with `AI_NOT_CONFIGURED` at the next patient message, so the failure belongs at the admin's click. Two 409s encode the gapless-cutover ordering: the **active config cannot be deleted** (activate a replacement first) and **only the active config can be tested** (that is the one a patient message would use). `/test` sends a real 16-token `ping` through the real adapter path — key, base URL, and model proven together, no session created — and reports failure as a 200 with `isSuccessful: false` plus the vendor's readable reason, persisted to `lastTestResult`. **`AiChatbotService`** runs the exchange: ownership check, provider resolution, history replay capped at 20 turns (a transcript is unbounded, a completion request is not), the upstream call, then both turns persisted with the provider audit trail. The **user turn is persisted before the call**, so a provider failure still records what was asked. The **disclaimer is structural** — every assistant turn persists `disclaimerShown: true` and the text rides in the envelope's `meta`, never inside the content, so a model cannot edit it away and a client cannot render a reply without receiving it. The assistant turn is stamped one millisecond after the user turn, using the `createdAt` seam `P13-T03` added, so the transcript can never render the reply first. Per-channel system prompts encode the §3.1 hard rules on the provider side — the first line, not the only one: `P13-T07`'s service-side guards are the control, and `contextPayload` stays empty until `P13-T06`. **Nothing chat-related is exposed over HTTP yet** (T08 owns that) and `AI_CHAT_ENABLED` defaults false, gating session creation and sending while leaving transcript reads available so a clinic pausing AI does not lose its history. Coverage: 39 unit cases across two service specs, plus a live smoke test against the running API — validation 400s, the two 409 guards, a keyless Ollama create, key rotation returning 503 on a deployment without `AI_PROVIDER_ENCRYPTION_KEY`, and a `/test` that reached a **real local Ollama daemon** and mapped its 404 to `AI_PROVIDER_MODEL_NOT_FOUND`.
6. `P13-T06` Context enrichment via domain services (post-SATUSEHAT read models — read-only, redacted). **Done**, behind `AI_CHAT_CONTEXT_ENRICHMENT_ENABLED` (default false) — the gate this plan's dependency note requires, and with it off the provider receives no patient data at all. Two properties make `ChatContextEnrichmentService` safe by construction rather than by care. First, **every read goes through the owning domain service as the authenticated user** (`PatientManagementService`, `AppointmentManagementService`, `RegistrationFlowService` — the three modules now export their service; no foreign repository is touched), so the domain's own `:own` scoping decides visibility and the chatbot can never assemble context the user could not already read themselves. Second, the result is **projected down to exactly the §5.3 fields and then passed through a `redactChatContext` denylist** — a defence-in-depth sanitizer that strips any key containing nik/bpjs/mrn/note/diagnos/allerg/token/secret/patientId/email/phone/address, drops arrays outright (a list is a bulk export, never context), and prunes objects that redact to nothing. That matters because the source rows are *not* safe: `AppointmentListItem` carries `patient.mrn`, `reason`, and `notes`, and the spec asserts none of them survive. Patient channel sends display name, next-appointment summary (time, doctor name, specialty, status) and today's queue number; doctor channel sends counts and its own next slot time only — **never a patient name**, so the doctor channel cannot become a bulk export route. "Next appointment" scans a bounded 30-day/100-row window because appointment lists come back newest-first; a patient beyond it gets no line rather than a wrong one. Enrichment is **best-effort**: a forbidden or failing domain read degrades that field to absent (the normal case when the other channel's account type has no matching profile), logged by field name only — a missing summary must never cost a patient their answer. Orchestration folds the payload into a **second system message behind a preamble that marks it reference data and explicitly not an instruction** (the prompt-injection boundary between HMS context and user text), and **persists it as its own SYSTEM turn** — the UU PDP audit question is "what personal data went to the processor, and when", and that row is the answer. Stored SYSTEM turns are then **excluded from history replay**, so a long conversation never resends several stale snapshots of a patient's appointments alongside the current one. Coverage: 42 unit cases — the full redaction denylist, both channels' projections asserted to exclude MRN/notes/names, earliest-upcoming selection from a newest-first list, cancelled-status filtering, clinic-timezone queue matching, degradation when reads fail, and the orchestration's context injection, SYSTEM-turn persistence, and no-stale-replay behaviour.
7. `P13-T07` Safety policy service (input/output guards, disclaimer injection, safety tags). **Done.** The per-channel system prompts and the T06 context preamble *ask* a model to behave; `SafetyPolicyService` is what *makes* it — every rule holds whether or not the provider cooperated. Three shapes of control, chosen per failure mode. **Refuse** (`AI_SAFETY_BLOCKED`) for input that attacks the policy itself: prompt injection and clinician impersonation have no legitimate reading, so they never reach the provider and never cost a token — and because the content checks run before the rate-limit query, a refused prompt costs no database round trip either. **Answer without the provider** for emergencies: an emergency pattern short-circuits the whole upstream path and replies from a deterministic bilingual template naming 119/112 and the IGD, because when someone describes chest pain the right answer must not depend on an API being reachable or a model choosing well — and emergencies deliberately **bypass the rate limit**, since a quota is an anti-abuse measure and withholding the ambulance number over one is not a trade HMS makes. **Repair** for output: markup is stripped first (so an assertion cannot hide inside a tag), then a reply asserting a diagnosis or issuing a dose is *replaced* with channel-appropriate redirect copy — patient copy points to the clinic, doctor copy defers to clinical judgement, because a clinician is not being told to see a clinician — and merely over-confident phrasing keeps its answer and gains the uncertainty notice. Patterns live as reviewable data in one file and are **bilingual throughout**: an Indonesian clinic's patients type in Bahasa Indonesia, English, or both, and a guard that only reads English is not a guard. They are also deliberately assertion-shaped — "apa itu diabetes?" is exactly the general health information the patient channel exists to give, so only language that asserts a conclusion *about this person* or issues an order matches. Rate limits are counted **per user across every session** (a second conversation buys no fresh budget) and the daily session quota **counts soft-deleted sessions** (or the limit would be one DELETE away from meaningless). Every intervention writes a `safetyTags` value on the persisted turn, so the `P13-T11` review can count what the guards caught in production instead of assuming they were never needed; `AI_SAFETY_BLOCKED` and the new `AI_RATE_LIMITED` are typed for the T08 controller to map. Coverage: 54 unit cases — every denylist family in both languages, the general-question and drug-class negatives, quota boundaries and the emergency bypass, the markup sanitizer including tag-hidden assertions, and the orchestration wiring (guards precede provider resolution, escalation persists both turns and calls no provider, guarded output is what gets stored).
8. `P13-T08` Chat controller + OpenAPI + integration tests (multi-adapter mocks). **Done.** `/api/v1/chat` exposes the six §6 routes plus the admin support list; `openapi.yaml` and the Orval client are regenerated. Three interface decisions. **A foreign session id answers 404, not 403** — whether an id exists in another user's account is itself information, and the repository's ownership filters already make not-found the natural answer. **The admin support view requires the ANY scope explicitly**: the global guard only proves the actor may read *some* session, so the service resolves scope the way every other module does and **refuses rather than silently narrowing** — a support screen showing only the operator's own two conversations looks like an empty clinic, not a missing grant. **A dedicated `@Catch(AiChatbotError)` filter** keeps the typed code in the envelope, because §4.3.6 asks clients to branch on `AI_PROVIDER_TIMEOUT` and the global filter would flatten that to `BAD_GATEWAY`; statuses are chosen by who can fix the problem — 422 safety, 429 rate limit, 503 not-configured, 502 provider, 504 timeout, and notably **`AI_PROVIDER_UNAUTHORIZED` is a 502, not a 401**, since a patient can do nothing about an expired clinic API key and a 401 would read as their own session expiring. The filter is controller-scoped so its precedence over the catch-all is explicit at the call site. Coverage is a **21-case integration spec that runs the real chain** — controller, guards, safety policy, resolver, registry, both adapters, and the HTTP client — against a stubbed `fetch` answering in each vendor's own wire shape, with a **genuinely sealed API key in the mocked row** so the reveal step runs for real and the outbound `Authorization` header proves the seal → store → reveal → authenticate chain. It covers both adapters end to end (including Claude's top-level `system` field), the emergency template answering with **zero fetch calls**, a refused injection, a provider-returned diagnosis being rewritten, all four upstream-failure mappings, the user turn surviving a provider failure, and the RBAC/ownership matrix (401, 403 per route, foreign-session 404 on read *and* delete, ANY-vs-OWN on the admin view, malformed uuid, feature flag off). Two real defects surfaced and were fixed while writing it: the spec's global prefix did not match `main.ts`, and the stubbed config row's fake ciphertext exposed that nothing had previously exercised decrypt-on-send.
9. `P13-T09` Frontend chat UI + admin provider settings page + Orval sync. **Done** (the Orval sync itself landed with `P13-T08`). The MVP shipped the assistant screen against a `ConversationService` interface with a comment promising the Phase 13 client would be a drop-in replacement — it was, so the panel's layout, thread, and composer are unchanged and only the service behind them is new. Three decisions in the chat client. The **session is created lazily on the first message**, not on mount: opening the screen and typing nothing must not consume a row or count against the daily quota. The session id lives inside the service instance, so **"new consultation" rebuilds the service** — replacing the instance is what starts a genuinely new server-side session, and a failed create clears the cached promise so the next attempt retries instead of rejecting forever from a settled one. The **disclaimer is read from the response envelope's `meta` and rendered per message**, never from a string the UI holds: the server owns the wording, and a reply that arrived without one must not render as though it had been shown. Replies come back as plain text and are split on blank lines — nothing is parsed as markdown, since anything richer is markup a provider could smuggle instructions through. The scaffolding that was honest in the MVP and would now be false is **deleted**: the mock conversation service, the static recent-history fixture (replaced by the real session list), and the "Pratinjau — respons simulasi" preview badge; the suggested prompts survive under a non-`mock` name because they are UX affordances whose text is sent as a real message. The **admin provider page** (`/admin/ai-providers`, gated on `AiProviderConfig` read with write as a separate grant, so a read-only holder sees the list without the buttons) covers create, edit, activate, test, and delete: the API key field shows only `••••hint` and stays blank on edit unless the admin is deliberately rotating, delete is disabled on the active config because the API refuses it, and a **failed connection test surfaces the provider's own reason** rather than a generic error — it arrives as a 200 carrying the outcome. Nav entry, and full en/id strings for both surfaces. Coverage: 18 new UI cases including that no session is created before the first message, that one session is reused across turns, that the rendered disclaimer is the one `meta` carried, and that a read-only holder sees no mutating control.
10. `P13-T10` UI tests, Indonesian i18n strings, feature-flag wiring, provider-not-configured states.
11. `P13-T11` Readiness review: safety checklist, UU PDP log audit, rate-limit load test, staging-only enablement.

Rationale: incumbents already ship clinical AI (e.g. Assist.id voice-to-EMR/ICD suggestion), so the chatbot is UX polish — not the market wedge. Compliance and EMR depth come first.

## 9. Phase 14 - Antrean Online / Mobile JKN Bridging (Backend + Frontend, 6 Tasks)

Goal: let a JKN member take a queue number at the clinic from Mobile JKN, and let the clinic's real queue progress flow back to BPJS. Scheduled out of Phase 11 by `P11-T08` / ADR D-023 — this is a **second, bidirectional** BPJS integration, not a continuation of PCare bridging.

Full evaluation: [bpjs-antrean-online.md](./bpjs-antrean-online.md) — read before starting `P14-T02`.

1. `P14-T01` Per-poli queue numbering: composite `(queueDate, specialtyId)` counter alongside the clinic-wide roll, allocated inside the same registration transaction with the same atomic upsert, surfaced on the queue board. The `P8-T06` follow-through. **The only task with no external dependency** — buildable now, and independently useful the moment a clinic runs more than one poli.
2. `P14-T02` Spike: obtain the pilot clinic's **Antrean-service** credentials; confirm the FKTP endpoint set, whether FKRTL's task-ID vocabulary applies or only `panggil` (status + waktu), whether HFIS poli/doctor codes match the synced PCare catalog, and the inbound token scheme. Output: ADR + recorded fixtures.
3. `P14-T03` `BpjsAntreanConfig` (separate row from `BpjsPcareConfig` — separately issued and separately revoked credentials, same `BpjsCredentialCryptoService` and singleton index pattern) + outbound adapter reusing the D-022 codec and HMAC builder; admin settings surface with write-only secrets and a `ref/poli` test connection.
4. `P14-T04` Inbound WS module: the six BPJS-called services behind a purpose-built token guard (never `JwtAuthGuard`), source-IP allowlist, per-endpoint rate limiting, system-actor provenance on every created row, audit on every call, and BPJS's own response envelope. Calls domain services, never repositories. **Security-critical — review it as such.**
5. `P14-T05` Outbound publishing: `antrean/add` (walk-ins only — provenance skips Mobile JKN bookings, which are already BPJS's rows), `panggil`, and `batal` as new outbox types on the existing worker and `P11-T07` monitor; HFIS reconciliation screen (compare `ref/poli`/`ref/dokter` and upcoming sessions against HFIS, report drift — never sync).
6. `P14-T06` UAT support: run BPJS's Antrol v2 FKTP checklist against the deployed pilot, re-record fixtures from real responses, and add the onboarding runbook entry (branch-office request, public-IP requirement, credential intake, UAT walkthrough).

Phase 14 notes:

- External prerequisites, all outside the codebase: a pilot clinic already running PCare bridging in production, its branch-office request for Antrean-service credentials with the facility profile flagged as having a queue system, and a deployment with a public IP and TLS that someone is accountable for. A clinic deployment behind NAT cannot run this feature at all.
- HFIS (not HMS) is the source of truth for poli, doctors, shifts, and quota that Mobile JKN renders. HMS owns only whether it can honour them.

## 10. Sequencing Rules

- Phase 7 must land before Phases 8-11 (they all consume the new fields). Phases 8 and 9 can proceed in parallel after Phase 7. Phase 10 requires Phase 8. Phase 11 requires Phases 7-8 from `P11-T03` onward; its spike (`P11-T01`) and config/adapter task (`P11-T02`) can start anytime, and both are gated externally on a pilot clinic's BPJS branch-office bridging request. Phase 13 requires Phase 10 (`P10-T06`); Phases 11-12 may proceed in parallel with Phase 13 backend tasks but context enrichment (`P13-T06`) must not ship to production until SATUSEHAT master-data linkage is verified.
- Phase 14 requires Phase 11 complete and in production at a pilot clinic; `P14-T01` (per-poli queue numbering) is the exception and may land at any time after `P8-T06`. `P14-T02` onward are gated externally on Antrean-service credentials and a publicly reachable deployment (D-023).
